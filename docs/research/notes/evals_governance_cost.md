# Evaluating, governing and cost-controlling autonomous coding agents (2025-2026), stress-tested against Guild

Research date: 2026-10-26. Every finding carries the publication date and a source-type tag:
[INDEPENDENT] = academic or non-vendor measurement; [VENDOR] = a vendor reporting on its own product or selling in the space; [SECONDARY] = a summary I could not check against the primary source; [OLDER] = before 2025.
Each finding ends with "Guild:" and one of SUPPORTS, CONTRADICTS, MISSING (Guild has no equivalent) or REFINES (Guild's choice holds but needs a detail added).

Guild choices referenced: drills (a replay suite of past issues and PRs with known right outcomes that must pass, with no quality drop and the cost delta reported, before any change to a prompt, skill, model or Claude Code version); pinned model IDs; quality metrics (steward override rate of triage, reviewer catch rate, escaped defects, time to first response, cost per merged change) with a monthly retrospective; deterministic risk tiers computed from file paths (T0 auto-merge up to T3, which needs two humans and a manual run); a Reviewer on a different model from the Builder; at most two Builder attempts, then escalation; cost per run from `total_cost_usd`; per-run `--max-budget-usd`; a monthly hard cap through a workspace spend limit; model routing (small model for triage, mid for building, strongest for review and spec work); a roadmap ordered by expected value per expected cost; two weeks of shadow mode before auto-merge is enabled.

## (a) Agent evaluation practice: replay and regression suites, benchmarks and their critiques, pass@k vs pass^k, LLM-as-judge, detecting regressions when models or harnesses change

### Takeaway
2026 practice converges on Guild's core idea: small regression suites drawn from real past failures, run on every model and harness change. But the evidence adds three hard requirements Guild does not yet state. (1) Run several trials per drill and track pass^k, because single runs are noisy and infrastructure alone moves scores by several points. (2) Grade beyond "tests pass", because about half of test-passing agent patches would not be merged by maintainers. (3) Protect drills from contamination and from leakage through git history, because replayed public issues are exactly what models memorise. Anthropic's own April 2026 postmortem also shows that eval suites can miss harness regressions, so Guild needs a soak period and production metrics as a second line of defence.

### Cited Findings

**Eval design guidance (vendor, but the most specific available)**
- Anthropic, "Demystifying evals for AI agents" (2026-01-09) [VENDOR]. It defines task, trial, grader, transcript and outcome, and grades the *outcome* (the final environment state), not what the agent claims. "Capability evals" should start at a low pass rate. "Regression evals" should sit near 100% and run continuously, and capability tasks "graduate" into the regression suite once they pass reliably. - [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Guild: SUPPORTS drills as a regression suite; MISSING a separate capability suite that measures headroom for model upgrades.
- Same post: "20-50 simple tasks drawn from real failures is a great start". Begin with manual pre-release checks, then add items from the bug tracker and support queue, prioritised by user impact. A 0% pass rate across many trials usually means a broken task, not an incapable agent. Balance "should trigger" and "should not trigger" cases. - [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Guild: SUPPORTS sourcing drills from past issues and PRs; REFINES by adding negative drills (for example, issues where the right triage is "close", "needs info" or "do nothing") so that triage tuning is not one-sided.
- pass@k is the probability of at least one success in k trials and rises with k. pass^k is the probability that all k trials succeed and falls with k. Example: 75% per-trial success gives pass^3 of about 42%. Use pass^k "where consistency is essential". - [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Guild: MISSING. A gate with "no quality drop" needs a defined metric and a trial count. Auto-merged T0 changes are a consistency use case (pass^k). "At most two Builder attempts" is in effect a pass@2 design.
- Grader guidance: code-based graders are fast and objective but brittle. Model-based graders need human calibration. Let LLM judges answer "Unknown". Use an isolated judge per dimension. Grade what was produced, not the exact path, because rigid step checks are "overly brittle". For coding agents, unit tests plus an LLM quality rubric "usually suffice". - [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Guild: REFINES. Drill graders should combine the original PR's tests with a calibrated rubric, not compare against the historical diff.
- Environment isolation: shared state between trials can inflate scores. The post's example is Claude reading the git history from earlier trials. - [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Guild: MISSING and critical. A replay drill checks out a past commit of a repository whose later history contains the real fix. Drills must strip future commits, tags, remote refs and the PR thread, or the Builder can find the answer.
- Read transcripts before trusting scores. Opus 4.5 scored 42% on CORE-Bench before grader and task fixes and about 95% after. - [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Guild: REFINES. The monthly retrospective should sample drill transcripts, not only pass/fail counts.
- With a prepared regression suite, teams can "upgrade in days" when a new model ships. - [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Guild: SUPPORTS gating model changes on drills.

**Noise and statistical power**
- Anthropic, "Quantifying infrastructure noise in agentic coding evals" (2026-02) [VENDOR]. On Terminal-Bench 2.0, with model, harness and tasks held constant, the gap between the most- and least-resourced of six container configurations was 6 percentage points (p < 0.01). Up to about 3x resource headroom mainly removes spurious out-of-memory kills; beyond that, agents solve tasks they otherwise could not. - [Anthropic](https://www.anthropic.com/engineering/infrastructure-noise); summary in [ZenML](https://www.zenml.io/llmops-database/infrastructure-noise-in-agentic-coding-evaluations). A secondary summary says to treat leaderboard gaps under 3 points with scepticism until configurations match; I did not confirm that wording in the post. - [Gigazine](https://gigazine.net/gsc_news/en/20260206-quantifying-infrastructure-noise-agentic-coding). Guild: REFINES. Drills must run on fixed runner resources and timeouts, or "no quality drop" will fire on noise.

**Public benchmarks: contamination and inflated scores**
- OpenAI stopped reporting SWE-bench Verified (2026-02-23) [VENDOR, about a benchmark it co-created]. Reasons given: the benchmark is "increasingly contaminated", and an audit of 138 of the hardest problems (about 27.6% of the set) found 59.4% with material problems in test design or problem statements. GPT-5.2, Claude Opus 4.5 and Gemini 3 Flash Preview could reproduce some original fixes from memory. OpenAI recommends SWE-bench Pro. The direct fetch returned HTTP 403, so these figures come from the search-result summary. - [OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/); coverage in [Latent Space](https://latent.space/p/swe-bench-dead). Guild: CONTRADICTS an unguarded drills design. Guild's drills are public OSS issues and PRs from a public repository, so future models may have trained on them. Drill pass rates for a *new* model may be inflated by memorisation, which is exactly the decision drills are meant to inform.
- SWE-bench Pro (Scale AI; arXiv 2509.16941, 2025-09) [INDEPENDENT-ish: Scale sells data]. 1,865 instances across 41 repositories: 731 public, 858 held-out and 276 commercial, the last from private startup code. On the commercial set, best models score below 20%. GPT-5 fell from 23.1% to 14.9% and Claude Opus 4.1 from 22.7% to 17.8%. - [arXiv](https://arxiv.org/pdf/2509.16941); [Scale](https://scale.com/blog/swe-bench-pro). A reported May 2026 Datacurve audit says Pro's graders mis-graded about a third of trials; I could not verify it. - [Buildmvpfast summary](https://www.buildmvpfast.com/blog/benchmark-contamination-ai-coding-leaderboard-swe-bench-2026). Guild: SUPPORTS keeping a private held-out part of the suite.
- SWE-rebench (arXiv 2505.20411, 2025-05) [INDEPENDENT]. More than 21,000 tasks and a continuously refreshed, decontaminated leaderboard. GPT-4.1 dropped from 31.1% to 26.7% between January 2025 and March-April 2025 tasks, which suggests contamination inflates some scores. - [arXiv](https://arxiv.org/pdf/2505.20411). SWE-bench-Live (arXiv 2505.23419, NeurIPS 2025) [INDEPENDENT]: 1,319 tasks from issues created since 2024 across 93 repositories, with a "substantial performance gap" against static SWE-bench. - [arXiv](https://arxiv.org/abs/2505.23419). Guild: MISSING a refresh policy. Add new drills continuously and report pass rates separately for drills created after a model's training cutoff.

**Tests passing is not the same as mergeable**
- METR research note (2026-03-10) [INDEPENDENT]. Four active maintainers of scikit-learn, Sphinx and pytest reviewed 296 AI-generated PRs that passed SWE-bench Verified, blinded to authorship. The PRs came from Claude 3.5 Sonnet through Claude 4.5 Sonnet and GPT-5. The maintainers re-approved only about 68% of the original human "golden" patches. Normalised to that baseline, maintainer merge rates were 24.2 pp (SE 2.7) below the automated grader; unnormalised, the gap was 34.9 pp. Claude Sonnet 4.5's 50%-time-horizon is about 50 minutes by the automated grader but about 8 minutes by maintainers, roughly a 7x overstatement. Rejection categories: code quality, breaking other code, core functionality failure. Caveats: no iteration on feedback, no CI, 3 repositories, and the newest model tested is Claude Sonnet 4.5. - [METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/). Guild: REFINES strongly. A drill's "known right outcome" must include maintainer-level acceptance criteria (repository standards, no collateral breakage), not just the PR's tests. The 68% golden-patch baseline also shows that even human maintainers disagree with themselves, so drill grading needs a stated tolerance.

**Capability trend context**
- METR time horizons [SECONDARY only]: Claude Opus 4.5 is reported at about 5 h at 50% reliability, and Opus 4.6 at about 12 h (95% CI 5.3-66 h). Doubling time is reported as about 4-7 months depending on the window. METR flags measurements above 16 h as unreliable on its current suite. - [GreaterWrong](https://www.greaterwrong.com/posts/EYb2K9acKfyG2bome/metr-time-horizons-now-10x-year); [Dror Poleg chart](https://www.drorpoleg.com/charts/task-horizon/). Guild: neutral context. Typical library issues are well within these horizons, but per the METR maintainer note the *mergeable* horizon is much shorter.

**Regressions from harness and infrastructure changes, not only from models**
- Anthropic, "April 23 postmortem" (2026-04-23) [VENDOR, primary]. Three Claude Code *product-layer* changes degraded quality while the API and models were unchanged:
  1. The default reasoning effort changed from high to medium (2026-03-04 to 04-07; Sonnet 4.6 and Opus 4.6).
  2. A thinking-cleanup bug ran on every turn instead of once (03-26 to 04-10).
  3. A verbosity-limiting system-prompt line hurt coding quality (04-16 to 04-20; Sonnet 4.6, Opus 4.6 and Opus 4.7).

  "Neither our internal usage nor evals initially reproduced the issues". The changes passed code reviews, unit tests, end-to-end tests and dogfooding. Remedies announced: broad per-model evals for every system-prompt change, line-by-line ablations, gating model-specific changes to their target models, and "soak periods, broader evals, and gradual rollouts" for changes that might trade off intelligence. - [Anthropic](https://www.anthropic.com/engineering/april-23-postmortem); [InfoQ](https://infoq.com/news/2026/05/anthropic-claude-code-postmortem). Guild: SUPPORTS gating Claude Code version changes on drills (pinned model IDs alone would not have prevented any of the three). REFINES: pin the effort level and other defaults explicitly, because a CLI default changed silently. CONTRADICTS treating drills as sufficient: the vendor's own evals missed all three, so production metrics and a soak period must back them up.
- Anthropic, "A postmortem of three recent issues" (2025-09-17) [VENDOR]. Infrastructure bugs (context-window misrouting, TPU output corruption, a compiler issue) intermittently degraded responses in August-September 2025. Initially 0.8% of Sonnet 4 requests were affected; a secondary source puts the peak at 16% of Sonnet 4 traffic on 2025-08-31. Detection was slowed partly by privacy limits on inspecting user traffic. - [Anthropic](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues); [implicator.ai](https://implicator.ai/anthropics-postmortem-three-bugs-pushed-claude-degradation-to-16-at-peak). Guild: CONTRADICTS the assumption that a pinned model ID means constant behaviour. Guild's monthly metrics are the only detector of serving-side drift between drill runs, and a month is a long detection window.

**LLM judges and reviewer agents**
- Spotify "Honk" background coding agent (2025-12) [VENDOR-user, engineering blog]. Deterministic verifiers run first, then an LLM judge compares the diff with the prompt. The judge vetoed about 25% of sessions, and the agent course-corrected in about half of those. The most common trigger was the agent going beyond the prompt's scope. Spotify said it had not yet built evals for the judge. - [Spotify Engineering](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3). InfoQ (2026-03) reports the judge was later dropped as too rigid (it blocked valid changes) once models improved. Spotify's posts and InfoQ conflict on its current status. - [InfoQ](https://infoq.com/news/2026/03/spotify-honk-rewrite). Guild: SUPPORTS a Reviewer plus a bounded retry loop: about half of vetoed attempts recovered, which argues for a second Builder attempt that uses Reviewer feedback. MISSING: evals for the Reviewer itself, measuring false vetoes as well as catches. The reviewer catch rate alone does not show over-blocking.
- "Correlated Errors in Large Language Models" (Kim, Garg, Peng, Garg; ICML 2025, PMLR 267) [INDEPENDENT]. Across more than 350 LLMs, models agree on the same wrong answer 60% of the time when both err on one leaderboard. Larger, more accurate models have more correlated errors *even across providers and architectures*, and models from the same organisation are more correlated. - [PMLR](https://proceedings.mlr.press/v267/kim25e.html); [arXiv](https://arxiv.org/abs/2506.07962v1). Guild: SUPPORTS a Reviewer on a different model, but only partly. If both are Anthropic models, they share an organisation, which the paper links to higher correlation. A cross-provider reviewer would reduce correlation further, but not remove it. The real independence comes from deterministic checks and humans.
- Self-preference bias (judges rate their own family's outputs higher) is widely reported. The sources I found were glossaries and blogs citing 2025 studies on GPT-4o and Claude 3.5 Sonnet. I could not reach a primary paper, so treat this as directional only. - [PromptLayer glossary](https://www.promptlayer.com/glossary/self-preference-bias). Guild: SUPPORTS the Reviewer-on-different-model choice (weak evidence).

### Inferences
- With roughly 20-50 drills and one trial each, a "no quality drop" gate cannot tell a real 5-point regression from the 6-point infrastructure swings Anthropic measured. Guild should run each drill k = 3-5 times on fixed hardware, report pass@1 and pass^k with binomial confidence intervals, and set the block threshold to a drop larger than the measured run-to-run noise. Otherwise the gate will either block constantly or be ignored.
- Drills need at least three grader layers: the original PR's tests (correctness), a rubric for maintainer acceptance (METR's rejection categories: quality, collateral breakage, core failure), and cost and turn counts. Comparing against the historical diff would penalise valid alternatives, which Anthropic's "grade outcomes, not paths" advice warns against.
- Contamination cuts both ways for Guild. Old drills inflate new-model scores, and a model that memorised the fix will pass while doing worse on fresh issues. Keep a "fresh" drill bucket (issues created after the candidate model's knowledge cutoff) and give that bucket's result the deciding weight in model-change decisions.
- Because harness-level changes (effort defaults, system prompts, context clearing) caused the April 2026 regression, "Claude Code version change" deserves the same gate as a model change, and the pinned state should include the CLI version, the effort level and the settings file, not just the model ID.

### Gaps
- I found no published, quantitative account from a company of an internal replay suite built from its own past tickets (size, pass-rate thresholds, false-block rate). Anthropic's guidance is generic, and Spotify's posts describe verifiers, not a replay suite.
- OpenAI's eval guidance on regression gating (cookbook or docs) was not fetched. The SWE-bench Verified post returned HTTP 403, so its figures come from search summaries.
- Anthropic's "Adding error bars to evals" (2024, [OLDER]) was not fetched; I found no 2025-2026 primary guidance on sample sizes for agent regression gates.
- METR's primary time-horizon figures for 2026 models were not verified (secondary sources only). Terminal-Bench 2.0's design was not researched beyond its use in the noise study.

## (b) Measured productivity and quality effects of coding agents, review burden and automation bias

### Takeaway
Independent evidence on speed is mixed and weak. METR's 2025 RCT found experienced open-source maintainers were 19% slower. METR's 2026 follow-up suggests a speedup but calls its own data "very weak evidence". The consistent signals across independent and vendor sources concern quality and review: AI raises change volume and PR size, review time and churn rise, and several datasets show more defects or incidents per change. Human reviewers of agent PRs show measurable habituation: approval rates rise while inline comments fall. The steward's own scrutiny is therefore a quantity Guild must measure, not assume.

### Cited Findings

**Speed: independent randomized and quasi-experimental evidence**
- METR RCT (2025-07-10) [INDEPENDENT]. 16 experienced open-source developers, 246 real issues (about 2 h each) in mature repositories averaging more than 22k stars and more than 1M LOC, randomised to AI-allowed or AI-disallowed. Tools were mainly Cursor Pro with Claude 3.5/3.7 Sonnet. With AI allowed, issues took 19% longer. Developers had forecast a 24% speedup and afterwards still believed AI had sped them up by about 20%. Caveats: small sample, specific setting, possible learning effects beyond about 50 h of Cursor use. - [METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/). Guild: SUPPORTS measuring outcomes rather than perceptions (Guild's metrics are behavioural, which is good). It also warns that a maintainer of a mature library, Guild's exact setting, is the population where gains were weakest.
- METR follow-up on late-2025 tools (2026-02) [INDEPENDENT, SECONDARY reporting]. Returning developers: an estimated 18% speedup (CI roughly -38% to +9%; sign conventions differ across reports). Newly recruited: about 4% (CI -15% to +9%). METR says developers are probably more sped up in early 2026 than in early 2025, but its data is "only very weak evidence" of the size, because many developers refused to be randomised to work without AI (selection bias) and pay was cut from $150/h to $50/h. It then surveyed 349 technical workers (February-April 2026). - [Birchtree summary](https://birchtree.me/blog/an-update-from-the-study-that-said-devs-were-actually-slower-with-coding-agents/); [I Programmer](https://www.i-programmer.info/news/99-professional/18910-perceived-value-of-ai-tools.html); [TechCrunch 2026-05-29](https://techcrunch.com/2026/05/29/coders-are-refusing-to-work-without-ai-and-that-could-come-back-to-bite-them/). The 2025 METR page itself notes the original results "are now out of date". - [METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/). Guild: neutral. There is no reliable independent effect size to plan around.
- Anthropic skill-formation RCT (2026-01-29) [VENDOR-run RCT]. 52 mostly junior engineers learning the Trio library. The AI-assisted group scored about 17% lower on a comprehension quiz (reported as about 50% against 67%), the speed gain was not statistically significant, and the biggest gap was on debugging questions. Participants who asked conceptual questions retained more. Critics note it measured immediate comprehension, not long-term skill. - [Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills); [Techzine](https://www.techzine.eu/news/applications/138507/ai-coding-tools-hinder-skill-development/); [InfoQ](https://infoq.com/news/2026/02/ai-coding-skill-formation/). Guild: MISSING. If agents do most of the building, the human steward's grasp of the codebase (needed for T2/T3 review and for judging escaped defects) can erode. Nothing in Guild keeps the steward hands-on.
- Google [VENDOR, SECONDARY]: Sundar Pichai cites about a 10% engineering-velocity gain (measured as engineering capacity created in hours per week) and an agent-assisted migration completed 6x faster than a year earlier. Reports that 75% of new code is AI-generated come from a single secondary source. An earlier Google RCT of 96 engineers reported 21% faster task completion ([OLDER], 2024). - [Business Insider](https://www.businessinsider.nl/sundar-pichai-says-ai-is-making-google-engineers-10-more-productive-heres-how-it-measures-that/); [DX newsletter](https://newsletter.getdx.com/p/how-much-does-ai-impact-development-speed). Guild: neutral context.

**Organisation-level survey evidence**
- DORA 2025 "State of AI-assisted Software Development" (2025-09-23) [INDEPENDENT-ish survey; Google-run]. Nearly 5,000 respondents plus more than 100 h of qualitative data. 90% use AI at work and more than 80% believe it raised their productivity. AI adoption now correlates *positively* with delivery throughput and product performance, but still *negatively* with delivery stability. 30% report little or no trust in AI-generated code. The central thesis: "AI doesn't fix a team; it amplifies what's already there". Without strong automated testing, mature version control and fast feedback loops, more change volume leads to instability. - [Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report). Guild: SUPPORTS Guild's dependence on a strong conformance harness ("the test suite is the product"), which is the kind of foundation DORA says gets amplified.
- The DORA AI Capabilities Model (2025-09-23) names seven capabilities that amplify AI's benefit: (1) clear and communicated AI stance; (2) healthy data ecosystems; (3) AI-accessible internal data; (4) strong version control practices (frequent commits, and rollback use, which helps AI-assisted teams); (5) working in small batches; (6) user-centric focus (without it, AI adoption can *hurt* team performance); (7) quality internal platforms. It is based on 78 interviews plus the survey; the blog gives directional results only. - [Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model); [dora.dev](https://dora.dev/ai/capabilities-model/). Guild: SUPPORTS (1) through AGENTS.md, (4) through squash-merge and Conventional Commits, and (7) through deterministic tiers and CI. MISSING an explicit small-batch limit on Builder PRs (maximum diff size per tier) and an explicit rollback drill. Value-per-cost ordering partly covers (6) if "value" means user value.

**Review burden, PR size, churn and defects (mostly vendor telemetry)**
- Faros AI "AI Productivity Paradox" (2025) [VENDOR telemetry, correlational]. 10,000 developers across 1,255 teams. High-AI-adoption teams completed 21% more tasks and merged 98% more PRs, while PR review time rose 91%, PR size 154% and bugs per developer 9%. There was no significant correlation with company-level improvement. - [Faros AI](https://www.faros.ai/blog/translating-ai-powered-developer-velocity-into-business-outcomes); [Augment summary](https://www.augmentcode.com/guides/ai-productivity-paradox-engineering-delivery). Guild: SUPPORTS cost per *merged* change and escaped defects over raw throughput.
- Faros AI "The Acceleration Whiplash" (Q2 2026) [VENDOR telemetry, correlational]. Two years of data, 22,000 developers, 4,000 teams, high against low adoption within the same organisations:

  | Area | Metric | Change |
  |---|---|---|
  | Throughput | Epics | +66.2% |
  | Throughput | Task throughput | +33.7% |
  | Throughput | PR merge rate | +16.2% |
  | Throughput | Deployments per week | -11.7% |
  | Review | PR size | +51% |
  | Review | Median review time | about 5x |
  | Review | Code churn | +861% |
  | Quality | Bugs per PR | +28.7% |
  | Quality | Bugs per developer | +54% |
  | Quality | Incidents per PR | +242.7% |
  | Quality | Monthly incidents | +57.9% |

  The methods are not disclosed and the data is behind a gate. - [Faros AI](https://faros.ai/research/ai-acceleration-whiplash). Guild: SUPPORTS tracking escaped defects and reviewer load. MISSING: churn and revert rate of agent-merged code, and PR size, as tracked metrics.
- CodeRabbit "State of AI vs Human Code Generation" (2025-12-17) [VENDOR; it sells AI review]. 470 OSS PRs (320 AI-coauthored, 150 human-only). AI PRs averaged 10.83 issues against 6.45 (about 1.7x). Relative to human PRs: 1.4x critical, 1.7x major, 1.75x logic and correctness, 1.57x security, 1.42x performance, and excessive I/O nearly 8x. CodeRabbit cannot guarantee that the "human" PRs were AI-free. - [CodeRabbit](https://coderabbit.ai/blog/state-of-ai-vs-human-code-generation-report); [The Register](https://www.theregister.com/2025/12/17/ai_code_bugs/). Guild: SUPPORTS a Reviewer focused on logic and correctness.
- GitClear "AI Copilot Code Quality 2025" (2025-02) [VENDOR analytics; data is two-thirds private companies and one-third OSS]. 211M changed lines, 2020-2024. Duplicated 5+ line blocks rose 8x in 2024, copy/pasted lines exceeded moved (refactored) lines for the first time, and moved lines fell about 40%. - [GitClear](https://www.gitclear.com/blog/ai_code_quality_2025_report); [DevClass](https://devclass.com/2025/02/20/ai-is-eroding-code-quality-states-new-in-depth-report/). A 2026 GitClear follow-up ("The Maintainability Gap", reported as covering 623M changes) gives these figures, but I could not find the primary page: moved code at 3.8% in 2026 (13% in 2023) and error-masking constructs up 47%. - [SECONDARY: Substack summary](https://haithembuilds.substack.com/p/the-agentic-shift-a-comprehensive). Guild: MISSING a duplication or refactor signal in the Reviewer rubric. For a library with generated tables and strict hygiene rules, duplication is a plausible failure mode.
- Anthropic Code Review for Claude Code (launched 2026-03-09) [VENDOR claims]. Internally, the share of PRs with substantive review comments rose from 16% to 54%, and engineers marked fewer than 1% of findings incorrect. Reviews average $15-25 and take about 20 min. The tool does not approve PRs. - [SD Times](https://sdtimes.com/ai/anthropic-brings-code-review-into-claude-code/). Guild: SUPPORTS a Reviewer agent and gives a cost benchmark for a strongest-model review per PR. All figures are unverified vendor numbers.

**Acceptance of agent PRs in the wild (independent, AIDev dataset)**
- The AIDev dataset (arXiv 2507.15003, 2025-07) [INDEPENDENT]: more than 456,000 PRs by OpenAI Codex, Devin, GitHub Copilot, Cursor and Claude Code across 61,000 repositories. Codex dominates the data (411,621 PRs; Claude Code about 1,500). - [alphaXiv](https://www.alphaxiv.org/abs/2507.15003v1). Three 2026 follow-up analyses report different acceptance rates depending on method; my mapping of figures to papers is uncertain. Codex: about 78-86%. Cursor: about 67-75%. Claude Code: about 66-72%. Devin: about 55-62%. Copilot: about 45-68%. One study puts the human-PR baseline at 82.6%. - [arXiv 2602.02345](https://arxiv.org/html/2602.02345v1); [arXiv 2602.04226](https://arxiv.org/html/2602.04226v1); [arXiv 2602.08915](https://arxiv.org/html/2602.08915v1). Guild: SUPPORTS escalation paths: many agent PRs are not accepted, so attempt limits and escalation matter.
- MSR 2026 Mining Challenge, "LGTM: Characteristics of Auto-Merged LLM-based Agentic PRs" [INDEPENDENT]. Maintainers auto-merge agentic PRs more often than human ones, but are more cautious when a PR deletes existing code. Auto-merged agentic PRs are smaller and more focused. - [MSR 2026](https://2026.msrconf.org/details/msr-2026-mining-challenge/61/LGTM-Characteristics-of-Auto-Merged-LLM-based-Agentic-PRs). Guild: SUPPORTS tiering by change shape. MISSING: deletions and diff size as tier inputs alongside file paths.
- arXiv 2605.08017 (2026-05) [INDEPENDENT]: in 61% of the bot-attributed merges among 29,585 PRs, a human had already completed review. The authors warn that merge logs do not show who made the governance decision. - [arXiv](https://arxiv.org/pdf/2605.08017). Guild: SUPPORTS an explicit audit record of *who decided* (tier, policy version, approvers), not just who clicked merge.

**Automation bias and review fatigue**
- "Habituation at the Gate" (arXiv 2606.22721, 2026-06-21) [INDEPENDENT, observational; read through an Emergent Mind summary]. 400 repeat reviewers and 11,429 reviews of Copilot, Devin, Codex and Cursor PRs (AIDev) over about 7 months. Within-reviewer approval of agent PRs rose from 30.1% to 36.8% (the abstract's figure; the body reports 27.9% to 42.4% by decile, so the figures are inconsistent). Inline comments fell 22% and words 28%, review latency rose about 3.5x, and PR size was flat. Approval of human PRs *fell* over the same period. The authors read this as "reflexive habituation under growing workload" rather than calibrated trust. Causation is not established. - [Emergent Mind](https://www.emergentmind.com/papers/2606.22721). Guild: CONTRADICTS assuming that T2/T3 human review stays effective. MISSING: monitoring the steward's scrutiny (comments per review, time on review, approval drift) and periodic seeded-defect checks of human reviewers, not only of the Reviewer agent.
- arXiv 2601.00753 (2026-01) [INDEPENDENT]: early-stage prediction of review effort for AI-generated PRs. It reports signals of possible "bot bias", with maintainers rejecting agent PRs faster. - [arXiv](https://arxiv.org/pdf/2601.00753). Guild: neutral; bias can run in either direction.
- Vercel engineering blog (2026, date unconfirmed) [VENDOR-user; the page returned HTTP 404 on fetch, so details come from the search snippet]. 58% of PRs in Vercel's largest monorepo merge without human review. Median merge time was 0.5 h for those PRs against 2.3 h for reviewed ones, and the revert rate matched the reviewed control group (2 of 513). The risk classifier flagged one incident-causing change as high risk, *but a human reviewer approved it anyway*. - [Vercel](https://vercel.com/blog/58-percent-of-prs-in-our-largest-monorepo-merge-without-human-review). Guild: SUPPORTS risk-tiered auto-merge. It also shows that human approval can override a correct high-risk flag, which argues for T3 requiring a manual *run* (as Guild does) and an explicit acknowledgement of the flag.

### Inferences
- The best-supported effect for Guild's design is downstream load, not speed. More, larger agent PRs raise review time and defect counts unless batches stay small. Guild's T0 auto-merge is the main lever against reviewer load, and also the main source of escaped-defect risk.
- "Reviewer catch rate" is measurable only with ground truth. Guild should seed known defects (for example, mutations of past bugs from the drills) into a share of Reviewer runs. The same seeding can audit the human steward, given the habituation evidence.
- Two weeks of shadow mode on a small library will yield perhaps tens of PRs. By the statistical "rule of three", zero observed bad merges in n cases gives only a 95% upper bound of about 3/n on the bad-merge rate (about 15% for n = 20). Shadow mode should be ended by a minimum count of decisions (and combined with drill evidence), not by calendar time.
- Vendor telemetry (Faros, CodeRabbit, GitClear) and independent studies (METR, AIDev, Habituation) agree on direction (more volume, more review burden, quality risk) but not on magnitude. Guild should treat its own monthly metrics as the authority and the literature as priors.

### Gaps
- I did not fetch primary Microsoft or GitHub 2025-2026 productivity studies; the GitHub and Microsoft field experiments I know of are from 2023-2024 ([OLDER]). Not covered.
- I found no independent study of escaped-defect rates for *autonomously merged* agent PRs in open-source libraries specifically, and none on time to first response for agent-triaged issues.
- The METR February 2026 primary post and the 349-person survey results were not fetched (secondary reporting only), and the sign convention for the 18% figure is ambiguous across reports.
- I could not verify the GitClear 2026 primary report or the Vercel post's date and full methodology.

## (c) Governance: human-in-the-loop tiering, policy-as-code for merges, separation of duties, two-person rules, kill switches, staged rollouts and audit

### Takeaway
Platform vendors now ship the primitives Guild needs: path-scoped required reviewers (GitHub ruleset rule, GA 2026-02-17), merge queues, a rule that a requester's approval of an agent PR does not count, and human approval before agent-triggered workflows run. These make Guild's deterministic path tiers implementable as server-side enforcement rather than only as Guild's own code. No mature standard governs coding agents: NIST's agent initiative is still at concept-paper stage, and I found no ISO/IEC 42001 application to coding agents. Staged rollout is endorsed (Anthropic's postmortem promises soak periods and gradual rollouts), but I found no measured "shadow mode then auto-merge" case study.

### Cited Findings
- GitHub Copilot coding agent docs [VENDOR, current 2026]. Agent PRs open as drafts. If branch protection requires approvals, the developer who assigned the task "can approve the pull request, but your approval won't count toward the required number"; someone else must approve. Actions workflows triggered by the agent do not run until a user with write access clicks "Approve and run workflows". With "Require approval of the most recent reviewable push", the final push needs n+1 approvals. - [GitHub Docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/review-copilot-prs). The GitHub changelog of 2026-03-13 adds a repository setting to *skip* the workflow approval (the default still requires it). - [GitHub Changelog](https://github.blog/changelog/2026-03-13-optionally-skip-approval-for-copilot-coding-agent-actions-workflows/). Guild: SUPPORTS separation of duties (the requester cannot be the approver). REFINES: if Guild's agents run under a GitHub App or bot identity, decide explicitly whether the steward who triggered a run may approve it at T2.
- GitHub "required reviewer rule" GA (2026-02-17) [VENDOR]. Rulesets can require N approvals from designated teams for specific files and folders, with `!` negation patterns. It augments CODEOWNERS rather than replacing it. Rulesets also support required merge-queue use and code-owner review. - [GitHub Changelog](https://github.blog/changelog/2026-02-17-required-reviewer-rule-is-now-generally-available/); [GitHub ruleset docs](https://docs.github.com/en/enterprise-server@3.19/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). Guild: SUPPORTS path-based tiers and offers a server-side enforcement layer that does not depend on Guild's tier code being correct. REFINES: express T2 and T3 path sets as ruleset file patterns, so a bug or an agent edit in Guild's tier script cannot downgrade a change.
- Policy-as-code (OPA/Conftest) for agent changes [VENDOR and practitioner tutorials only]. The pattern described is a two-layer control: restrict the agent's reachable tools (MCP), then evaluate each proposed action against OPA policy before the pipeline executes it, failing closed. Conftest suits formats `opa eval` cannot parse. Policies need their own tests (`opa test`, `conftest verify`). - [DEV Community](https://dev.to/devopsstart/governing-ai-agents-in-cicd-with-opa-and-mcp-58lb); [Wiz Academy](https://www.wiz.io/es-es/academy/application-security/open-policy-agent-opa). Guild: SUPPORTS deterministic, tested tier code (equivalent in spirit; Guild's Python tier function plays the role of the policy). No independent evidence of effectiveness was found.
- NIST AI Agent Standards Initiative (CAISI, launched 2026-02) [INDEPENDENT/government]. It focuses on agent security, identity and authorisation, separately from the AI RMF. The NCCoE concept paper on agent identity and authorisation had a 2026-04-02 comment deadline. No finalised standard and no coding-agent guidance had been published as of the sources I found. - [NIST](https://www.nist.gov/artificial-intelligence/ai-agent-standards-initiative); [CASRAI guide](https://casrai.org/guides/nist-ai-agent-standards-initiative). Guild: no conflict, and no standard to adopt yet.
- Anthropic's April 2026 postmortem commitments [VENDOR] amount to a governance pattern for harness and prompt changes: per-model evals for every system-prompt change, review and audit tooling for prompt changes, gating model-specific changes to their models, and "soak periods ... and gradual rollouts" for risky changes. - [Anthropic](https://www.anthropic.com/engineering/april-23-postmortem). Guild: SUPPORTS drills plus shadow mode. MISSING: a soak period after *each* gated change (not only before the first auto-merge), and a review requirement for prompt and skill diffs. Treat Guild's own prompt and skill files as T3 paths.
- Claude Code telemetry governance [VENDOR docs]. OTel exporter variables should come from managed settings, a repository's `.claude/settings.json` cannot set exporter variables, and an endpoint set in managed settings removes developer-set endpoints. - [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage). Guild: REFINES. In CI, Guild's Claude Code configuration lives in the repository (`.claude/`, `AGENTS.md`, skills) that the Builder can edit. Those paths must be T3, or an agent PR could relax its own permissions, budget flags or prompts.
- Shadow mode [weak evidence]. The only explicit "shadow mode" definition I found is a community skill template: the agent runs beside the human process without delivering output, agreement is tracked, and humans sign off before promotion. - [claudskills.com](https://claudskills.com/skills/shadow-mode-runner/SKILL.md). Vercel's auto-merge reports outcome parity on 513 PRs but I could not confirm a shadow phase (see (b)). Guild: SUPPORTS shadow mode conceptually. No measured precedent for its length.
- Two-person rules under habituation [INDEPENDENT; see (b)]: approval drift and fewer inline comments among repeat reviewers of agent PRs. - [Emergent Mind / arXiv 2606.22721](https://www.emergentmind.com/papers/2606.22721). Guild: REFINES T3 (two humans). Two habituated approvers are weaker than they look; require the second approver to be someone other than the steward who triages daily where possible, and require a written risk note.

### Inferences
- Defence in depth for tiers: Guild's tier function should be reproduced, or at least bounded, by GitHub rulesets (path-scoped required reviewers, merge queue, required status checks). A drift check should fail CI if the tier code and the ruleset disagree. The tier code, the ruleset export, agent prompts, skills, `.claude/` settings and CI workflow files should all be T3.
- Kill switch: no source gave a canonical design. For Guild, the practical switches are (1) a repository variable or label checked at the start of every workflow, (2) revoking or exhausting the workspace spend limit (a hard stop at the provider), and (3) turning on the ruleset requirement for one human approval on all paths. All three should be tested in shadow mode.
- Audit: the arXiv 2605.08017 finding (merge logs hide who decided) implies Guild should write a per-run decision record (inputs, tier, policy version, model and CLI versions, cost, approvers) to an append-only place, such as a PR comment or a check-run summary.

### Gaps
- I found no ISO/IEC 42001 or NIST AI RMF profile applied specifically to engineering or coding agents, and no published Google or Microsoft *policy* text on agent-authored code (as opposed to tooling docs).
- I found no published measurement of how long a shadow phase must run, or of agreement-rate thresholds, for promoting coding agents to auto-merge.
- I found no evidence on kill-switch use or incidents for coding agents.

## (d) Cost telemetry, budgeting, caps, prompt caching, model routing, runaway costs and value-per-cost prioritisation

### Takeaway
Guild's cost design is mostly sound, but its "hard caps" are softer than assumed. `total_cost_usd` and `--max-budget-usd` both rely on Claude Code's client-side estimate at list price. The budget check happens per turn, so a run can overshoot its cap; one test overshot 8.4x on a single turn. The only true hard stop is provider-side, through the workspace spend limit, and Console-authenticated Claude Code uses a special workspace that cannot hold API keys. Prompt caching dominates per-run token volume, so changes to skills, tools or effort that invalidate the cache will show up as cost deltas in drills. Evidence that routers save money is strong for chat (2024) but weak for code: one robustness study found routers send all code queries to the strong model.

### Cited Findings

**Cost tracking and telemetry**
- Claude Code cost docs (current 2026) [VENDOR]:
  - Across enterprise deployments the average is about $13 per developer per active day and $150-250 per developer per month, with 90% of users below $30 per active day.
  - The `/usage` dollar figure is computed locally from token counts at list price, unless a managed `modelPricing` table applies. It is "an estimate"; for authoritative billing, see the Console usage page.
  - The same multiplied figure "counts toward `--max-budget-usd`".
  - Agent teams use about 7x the tokens of a standard session when teammates run in plan mode.
  - Background usage is typically under $0.04 per session.

  - [Claude Code docs: costs](https://code.claude.com/docs/en/costs). Guild: SUPPORTS cost per run from JSON output and the routing tiers (vendor guidance matches). REFINES: `total_cost_usd` is an estimate at list price. Reconcile it monthly against the Console usage page before using it in value-per-cost decisions.
- On idle and runaway token use, the Claude Code docs [VENDOR] document how long sessions cost more: each request resends the full context, cache misses after the TTL reprocess the full context, session-scoped scheduled tasks and `/loop` fire while idle, and goal check-ins wake idle sessions. Goal check-ins were "uncapped" before v2.1.246 and are now capped at three per goal. Compaction is itself a large request. - [Claude Code docs: costs](https://code.claude.com/docs/en/costs).   - [Claude Code docs: monitoring](https://code.claude.com/docs/en/monitoring-usage). Guild: REFINES. In June 2026 the GenAI conventions moved to a dedicated repository, and there has been churn (for example, per-message events replaced by aggregated `gen_ai.input.messages` and `gen_ai.output.messages` attributes in v1.37). - [DEV Community](https://dev.to/azena-ai/opentelemetrys-genai-semantic-conventions-are-not-stable-yet-heres-what-actually-shipped-in-2026-3mke); [Dash0](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained). **Caps: per-run and monthly**
- `--max-budget-usd` behaviour [INDEPENDENT test, single blog, 2026-04-18]. The docs say "print mode only". The test `claude -p --max-budget-usd 0.01 --output-format json ...` returned `subtype: error_max_budget_usd`, `is_error: true` and exit code 1, after spending `total_cost_usd` = $0.0844 (8.4x the cap) on a single turn. The author infers the check happens between turns, not within one. - [LinuxJedi](https://linuxjedi.co.uk/when-the-docs-fall-short-investigating-claude-codes-budget-cap/). A third-party post notes that on Pro/Max subscription auth the guard still compares the estimated cost, so it can stop runs the subscription would absorb. - [Aident](https://aident.ai/blog/fix-claude-code-max-budget-usd-subscription). Guild: CONTRADICTS treating `--max-budget-usd` as a hard per-run ceiling. Pair it with `--max-turns`, a wall-clock timeout in CI, and the provider-side monthly cap. Size the per-run cap so that cap plus one maximal turn still fits.
- Console spend limits [VENDOR]. Organisation and workspace limits are monthly, and amounts are given in minor units ("50000" = $500.00). Setting them through the API is in early-access preview. The Default workspace cannot have its own limit (third-party guide). A workspace rate limit can cap its share. - [Claude API spend-limit reference](https://platform.claude.com/docs/en/api/http/beta/organization/spend_limits/set.md); [Claude Code docs: costs](https://code.claude.com/docs/en/costs); [xray.tech guide](https://www.xray.tech/post/how-to-set-spend-limits-in-claude-console); workspace limits announced in 2024 ([OLDER], [Anthropic](https://anthropic.com/news/workspaces)). Guild: SUPPORTS a monthly hard cap through a workspace limit. REFINES: CI runs with an API key, so the key must live in a dedicated non-Default workspace with its own monthly limit; the auto-created "Claude Code" workspace cannot issue API keys. - LiteLLM proxy budgets [OSS docs]. Per-key `max_budget` with `budget_duration` (for example "30d") blocks requests once exceeded. Budgets need a Postgres database; without one, global `max_budget` is *not enforced* (only a startup warning). Team budgets override personal budgets for team keys. Soft budgets and alerts are available, as are per-model provider budgets. - [LiteLLM docs: budgets](https://docs.litellm.ai/docs/proxy/users); [LiteLLM: provider budget routing](https://docs.litellm.ai/docs/proxy/provider_budget_routing.md). Anthropic notes that several large enterprises use LiteLLM, which is "unaffiliated with Anthropic and has not been audited for security". - [Claude Code docs: costs](https://code.claude.com/docs/en/costs). Guild: probably unnecessary for a single-provider, single-repository setup. The workspace limit is simpler and is enforced by the provider.

**Prompt caching**
- Prompt caching pricing (current Claude API docs) [VENDOR]:
  - Writes: 5-minute cache writes cost 1.25x base input and 1-hour writes 2x.
  - Reads: cache reads cost 0.1x base input, but 0.05x on Opus 5.5 and Sonnet 5.5, and 0.025x on Fable 5.1 and Mythos 5.1.
  - TTL: default 5 minutes, refreshed on each use and measured from the *start* of the request.
  - Invalidation: the cache hierarchy runs tools, then system, then messages. Changing tool definitions invalidates everything; changing thinking or effort parameters invalidates messages.
  - Caches are isolated per workspace.

  - [Claude API docs: prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). The Claude Code docs' example session shows 940k cache-read tokens against 1.2k uncached input. - [Claude Code docs: costs](https://code.claude.com/docs/en/costs). Guild: SUPPORTS reporting the cost delta in drills, since a skill, MCP or tool-definition change can shift cost through cache invalidation without any change in quality. REFINES: drills should report cache-read and cache-write tokens separately, so a cost jump can be attributed. Running drills back to back inside the 5-minute TTL will understate cold-start costs that real, sporadic issue traffic pays.

**Model routing and cascading**
- RouteLLM (LMSYS 2024-07; ICLR 2025) [INDEPENDENT, OLDER for the core result]. Routers trained on preference data cut cost by more than 85% on MT-Bench, 45% on MMLU and 35% on GSM8K against GPT-4 alone, while keeping 95% of GPT-4's quality. - [LMSYS](https://lmsys.org/blog/2024-07-01-routellm/); [arXiv](https://arxiv.org/html/2406.18665v2). "How Robust Are Router-LLMs?" (arXiv 2504.07113, 2025-04) [INDEPENDENT]: re-evaluated routers sent *code* queries to the strong model 100% of the time, and results were fragile across query categories. - [arXiv](https://arxiv.org/pdf/2504.07113). A 2026 survey (arXiv 2603.04445) warns that routing papers measure savings in non-comparable units. - [arXiv](https://arxiv.org/pdf/2603.04445). Guild: REFINES. Learned routing is weak evidence for code. Guild's *static, role-based* routing (triage, build, review) is a different, simpler design; validate it per role with drills, not by citing router papers.
- Code cascades [INDEPENDENT]. "Model Cascading for Code" (arXiv 2405.15842, 2024, [OLDER]) runs the smallest model first, uses self-generated tests to decide whether to escalate, and reports up to 70% compute reduction at equal accuracy in the best case. Inter-Cascade (arXiv 2509.22984, 2025-09) reports up to 48% fewer strong-model calls and about 50% fee savings, though not code-specific. - [arXiv 2405.15842](https://arxiv.org/abs/2405.15842v1); [arXiv 2509.22984](https://arxiv.org/abs/2509.22984v1). Guild: SUPPORTS cheap-first patterns where a deterministic verifier (tests) decides escalation. Guild's "two Builder attempts then escalate" could escalate the *model* on attempt 2 rather than repeating the same model.

**Runaway-cost incidents (mostly anecdotal)**

**Value-per-cost prioritisation**
- I found no published method specific to agents for ordering a backlog by expected value per expected cost. The nearest evidence is Faros's finding that throughput gains do not translate into company-level outcomes (deployments per week fell 11.7% in high-adoption teams). - [Faros AI](https://faros.ai/research/ai-acceleration-whiplash). Guild: Guild's choice is reasonable but unsupported by literature. MISSING: a calibration step comparing predicted cost per item with the actual `total_cost_usd`, and predicted value with outcomes.

### Inferences
- Guild's caps should form a hierarchy:
  1. Per-run: `--max-budget-usd`, `--max-turns` and a CI timeout. These are soft and can overshoot by one turn.
  2. Per-day: an alert computed from the cost ledger.
  3. Per-month: the workspace spend limit, which the provider enforces and which is the only hard cap.
- Because cost per merged change will be dominated by cache reads of the repository context, keeping prompts, skills and tool definitions stable is a cost lever as well as a quality lever. The drill gate's "cost delta" is the right place to catch regressions. Report it as a distribution (median and p90 per drill over k trials), not a single number.
- Routing "strongest model for review" is consistent with the correlated-errors evidence (a different, stronger model). Static role routing has no published validation for code, so Guild's first drills should include a role-swap ablation (for example, mid model as reviewer) to check that the cost premium buys catch rate.

### Gaps
- I found no independent measurement of how closely `total_cost_usd` matches invoiced cost, or of `--max-budget-usd` overshoot beyond one informal test.
- I did not research Anthropic's official per-model list prices for October 2026 (for budgeting arithmetic); they are on the pricing page.
- I found no verified, primary-sourced runaway-cost incident specific to Claude Code headless runs in CI.
- I found no study of FinOps practice for agents at small open-source projects; all budget practice found is enterprise-oriented.
