# Architecture and workflow patterns for reliable multi-agent software development (2025-2026)

Scope: how practitioners structure agent roles, context, specs and harnesses for long-running or unattended coding work, used to stress-test **Guild** (a Claude Code plugin plus per-repo CHARTER.md, GUILD.md and `.claude/agents/*.md`; AGENTS.md as handbook; five roles Triage, Planner, Builder, Reviewer, Releaser with separate tool allowlists and models; GitHub issues as roadmap source of truth; steward comment commands parsed by a deterministic script; GitHub Actions running Claude Code headless; no beta-only features; portable across Anthropic API, Bedrock and Vertex).

Conventions used below:
- **[Independent]** = academic or non-vendor evidence; **[Vendor]** = claim by a company about its own product or approach (Anthropic, OpenAI, GitHub, Cognition, Spotify and Stripe count as vendors or practitioners reporting their own systems); **[Secondary]** = I only saw a search snippet or third-party summary, not the primary text.
- **→ Guild:** marks whether the finding *supports*, *contradicts*, or shows something *missing* in Guild's design.
- Research date: 2026-10-26. Older foundations are labelled as such.

## 1. Anthropic's published guidance: orchestrator-worker vs single agent, sub-agents, context, tools, skills, plugins, token costs

### Takeaway
Anthropic's own guidance is consistently "simplest thing first, add agents only where the task is parallelizable or context-bound." It has moved toward a small number of roles that keep **writes single-threaded**: a planner, one generator/builder, and a separate skeptical evaluator with fresh context, all talking through files and git, gated by deterministic checks. It also warns that every harness component encodes an assumption about model weakness that goes stale, and that multi-agent systems cost roughly 15x a chat in tokens and over 20x a solo run in dollars.

### Cited Findings

**Foundations (older, Dec 2024)**
- "Building effective agents" (Dec 19, 2024, older foundation) distinguishes *workflows* ("LLMs and tools are orchestrated through predefined code paths") from *agents* ("LLMs dynamically direct their own processes and tool usage"), and recommends "finding the simplest solution possible, and only increasing complexity when needed." It lists the patterns prompt chaining, routing, parallelization (sectioning and voting), orchestrator-workers and evaluator-optimizer. [Vendor] — [Anthropic, Building effective agents](https://www.anthropic.com/research/building-effective-agents)
  - → Guild: *supports* a fixed Triage→Planner→Builder→Reviewer→Releaser chain run by a deterministic orchestration script. That is a *workflow* (prompt chaining plus evaluator-optimizer) rather than a free-form multi-agent system, which is the lower-risk side of Anthropic's split.
- Same post: coding agents are a good fit because "Code solutions are verifiable through automated tests," but "human review remains crucial for ensuring solutions align with broader system requirements." It warns that frameworks "create extra layers of abstraction that can obscure the underlying prompts and responses." [Vendor] — [Anthropic, Building effective agents](https://www.anthropic.com/research/building-effective-agents)
  - → Guild: *supports* human merge and the steward role, and *supports* a thin orchestration script over a heavy agent framework.
- Same post, tool appendix: "Poka-yoke your tools." On SWE-bench, requiring absolute file paths fixed tool misuse, and "we actually spent more time optimizing our tools than the overall prompt." [Vendor] — [Anthropic, Building effective agents](https://www.anthropic.com/research/building-effective-agents)

**Multi-agent research system (Jun 13, 2025)**
- An orchestrator-worker system (Claude Opus 4 lead, Sonnet 4 subagents) beat single-agent Opus 4 by **90.2%** on Anthropic's internal research eval. [Vendor] — [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Token cost: agents use **~4x** the tokens of chat, multi-agent systems **~15x**. On BrowseComp, token usage alone explained **~80%** of performance variance (95% together with tool-call count and model choice). [Vendor] — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- When it hurts: domains "that require all agents to share the same context or involve many dependencies between agents" are a poor fit. Coding has fewer parallelizable tasks than research, and agents are not yet good at real-time coordination. [Vendor] — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
  - → Guild: *contradicts* any plan to run several Builders in parallel on one repo. It *supports* sequential roles that hand off artifacts.
- Operations: agents resume from the point of failure rather than restarting, using retries and regular checkpoints. Rainbow deployments shift traffic gradually so in-flight agents aren't broken by prompt or code updates. The lead saves its plan to external memory because context beyond 200k tokens is truncated. Subagents write outputs to external storage and pass "lightweight references" back. [Vendor] — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
  - → Guild: *supports* issues and PRs as durable external memory. *Missing*: a way to ship a new Guild plugin version without breaking runs already in flight (pin the plugin version per run; see section 6).
- Evaluation: start with ~20 real queries, because effect sizes are large early on. One LLM-judge prompt returning a 0.0-1.0 score plus pass/fail matched humans best. For stateful workflows, evaluate the end state rather than each step. [Vendor] — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
  - → Guild: *missing*: an eval set of about 20 real issues to replay when prompts, skills or models change.

**Context engineering (Sep 29, 2025)**
- Defines context engineering as curating "the optimal set of tokens" at inference and names "context rot": recall falls as the window grows, so models have a finite "attention budget." System prompts should sit at the "right altitude," between brittle hard-coded logic and vague guidance. Start minimal and add instructions only in response to observed failures. [Vendor] — [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Claude Code is a hybrid: "CLAUDE.md files are naively dropped into context up front," while glob and grep retrieve files just in time. Long-horizon techniques are compaction ("first lever"), structured note-taking (NOTES.md, to-do lists) and sub-agents that return condensed summaries of **~1,000-2,000 tokens**. [Vendor] — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
  - → Guild: *mixed*. Loading CHARTER.md, GUILD.md, AGENTS.md and a role file up front on every run spends attention budget. Only the parts every role needs should be eager-loaded; the rest belongs in skills or files read on demand.

**Writing tools for agents (Sep 11, 2025)**
- "More tools don't always lead to better outcomes." Consolidate multi-step operations into one tool, namespace related tools, return high-signal content, and paginate or truncate output (Claude Code caps tool responses at 25,000 tokens by default). A concise response format used 72 tokens against 206 for the detailed one. Develop tools against held-out evals. [Vendor] — [Anthropic, Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
  - → Guild: *supports* small per-role tool allowlists, and *supports* deterministic scripts that wrap multi-step `gh` sequences (e.g. "claim issue") instead of exposing raw `gh` to every role.

**Long-running harnesses (Nov 26, 2025)**
- Two-agent pattern, an **initializer** plus a **coding agent**, with "identical harnesses" and different prompts. The initializer writes `init.sh`, `claude-progress.txt`, a feature list of 200+ features all marked failing, and an initial git commit. Coding agents work **one feature per session**, may only flip the `passes` field, and commit after each feature. The rule: "It is unacceptable to remove or edit tests." JSON was chosen over Markdown because the model is less likely to overwrite it inappropriately. [Vendor] — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Observed failure modes: trying to one-shot the whole app, declaring victory early, marking features done without end-to-end tests, and wasting time working out how to run the app. A testing agent, QA agent or cleanup agent is listed only as *future work*, and the post leaves open whether one general agent or several specialized agents is better. [Vendor] — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
  - → Guild: *supports* "one issue → one PR" Builder runs and git as a checkpoint. *Missing*: a machine-readable progress or handoff artifact that agents may only change in narrow ways (e.g. a JSON checklist in the issue or PR body). *Note*: Anthropic itself did not claim that separate roles beat one agent here.

**Harness design for long-running apps (Mar 24, 2026)** — closest published analogue to Guild's Planner/Builder/Reviewer
- Three agents: a **planner** expands a 1-4 sentence prompt into a product spec focused on deliverables rather than technical detail; a **generator** builds sprint by sprint; an **evaluator** uses Playwright MCP to click through the running app and grade against hard thresholds. Agents communicate **through files**. [Vendor] — [Anthropic, Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Why a separate evaluator: agents "reliably skew positive when grading their own work," and tuning a standalone evaluator is "far more tractable than making a generator critical of its own work." The evaluator still leans generous, so it was calibrated with few-shot examples and score breakdowns. **Sprint contracts**: before coding, the generator proposes what it will build and how success will be verified, and the evaluator approves. [Vendor] — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Cost: solo run 20 min / **$9** (broken result) vs full harness 6 h / **$200**, "over 20x more expensive," with a clear quality difference (Opus 4.5). [Vendor] — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- On Opus 4.6 the sprint construct was **removed**, the evaluator moved to a single end pass, and the planner and evaluator stayed. The post's core lesson: "every component in a harness encodes an assumption about what the model can't do on its own," and those assumptions go stale. Context resets were needed for Sonnet 4.5's "context anxiety" and were dropped for Opus 4.5. [Vendor] — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps)
  - → Guild: *strongly supports* separating Planner, Builder and Reviewer and handing off through artifacts. *Missing*: (a) a "sprint contract" in which Planner and Reviewer agree on acceptance checks before the Builder starts; (b) a scheduled re-test of whether each role still earns its cost after each model upgrade.

**Building a C compiler with parallel Claudes (Feb 5, 2026)**
- 16 parallel Claude Code agents (Opus 4.6), **no orchestrator agent**, each in its own Docker container cloning a shared bare repo. Tasks are claimed by writing a lock file to `current_tasks/`, synced through git. About 2,000 sessions over two weeks, 2B input and 140M output tokens, **just under $20,000**, producing a 100k-line Rust compiler that builds Linux 6.9 on three architectures. [Vendor] — [Anthropic, Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)
- Lessons: "the verifier must be nearly perfect," because Claude solves whatever the tests define. CI was added because new work kept breaking old work. Keep output short and log to files, tagging failures with `ERROR` so grep finds them. Add a `--fast` 1-10% test sample to counter "time blindness." Parallelism worked for many independent failing tests and failed when all agents hit the same kernel bug. Specialized roles (dedup, performance, docs, design critic) were useful. The author is uneasy about mistaking passing tests for done work. [Vendor] — [same](https://www.anthropic.com/engineering/building-c-compiler)
  - → Guild: *supports* tests and oracles as ground truth, which fits confusable's conformance harness and ICU/Rust oracle fixtures. *Supports* git-based claiming (an assignee or label on the issue is the GitHub equivalent). *Supports* specialized maintenance roles. *Shows* that parallel writers only work when tasks are truly independent and CI gates every merge.

**Claude Code best practices (living doc, fetched Oct 2026)**
- "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." [Vendor] — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- Verification is central: "Give Claude a check it can run… It's the difference between a session you watch and one you walk away from." Gates come in rising strength: in the prompt, a `/goal` condition, a **Stop hook** that blocks the turn until a script passes, or a verification subagent. "The `/goal` and Stop hook versions are what let an unattended run finish correctly without you." [Vendor] — [same](https://code.claude.com/docs/en/best-practices)
  - → Guild: *supports* a Builder Stop hook that runs `uv run pytest` and pre-commit before the PR can open. *Caution*: `/goal` and dynamic workflows may not be stable features, so check before relying on them (Guild avoids beta features).
- CLAUDE.md: "keep it short." "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" For each line, ask "Would removing this cause Claude to make mistakes?" Put sometimes-relevant knowledge in skills. CLAUDE.md is advisory; "hooks are deterministic and guarantee the action happens." `@path` imports are supported. [Vendor] — [same](https://code.claude.com/docs/en/best-practices)
  - → Guild: *supports* putting enforcement (steward-command parsing, label transitions, budgets) in scripts and hooks rather than prose. *Risk*: CHARTER.md, GUILD.md, AGENTS.md and role prompts together can grow into the "over-specified CLAUDE.md" failure pattern.
- Writer/Reviewer: "A fresh context improves code review since Claude won't be biased toward code it just wrote." For adversarial review, a subagent "sees only the diff and the criteria you give it." Caveat: "A reviewer prompted to find gaps will usually report some, even when the work is sound… Chasing every finding leads to over-engineering," so tell the reviewer to flag only correctness and requirement gaps. [Vendor] — [same](https://code.claude.com/docs/en/best-practices)
  - → Guild: *supports* a separate Reviewer with fresh context. *Missing*: a rule bounding which Reviewer findings block the Builder, otherwise Builder and Reviewer can loop indefinitely.
- Plan first only when it pays: "If you could describe the diff in one sentence, skip the plan." Interview the user, write SPEC.md, then execute it in a fresh session. Good specs "name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step." [Vendor] — [same](https://code.claude.com/docs/en/best-practices)
  - → Guild: *supports* a tiered path map in which small tiers skip the Planner.
- Headless: `claude -p`, `--output-format json|stream-json`, `--allowedTools`, `--permission-mode dontAsk` for unattended runs ("denies anything else that would need approval"). Runs create resumable sessions unless `--no-session-persistence` is passed. [Vendor] — [same](https://code.claude.com/docs/en/best-practices)
- CLI over MCP: "CLI tools are the most context-efficient way to interact with external services. If you use GitHub, install the `gh` CLI." [Vendor] — [same](https://code.claude.com/docs/en/best-practices)
- Experimental surfaces listed in the same doc: "Agent teams: experimental and disabled by default"; "Agent view: research preview." [Vendor] — [same](https://code.claude.com/docs/en/best-practices)
  - → Guild: *supports* building on stable pieces (headless `-p`, subagents, hooks, skills, plugins) and not on agent teams.

**Claude Agent SDK (Sep 29, 2025)**
- The Claude Code SDK was renamed the Claude Agent SDK. Its loop is "gather context -> take action -> verify work -> repeat." Linting is "an excellent form of rules-based feedback." LLM-as-judge "is generally not a very robust method, and can have heavy latency tradeoffs." Subagents "use their own isolated context windows." [Vendor] — [Claude blog, Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
  - → Guild: *supports* deterministic checks as the primary gate, with the LLM Reviewer as a secondary gate.

**Agent Skills (Oct 16, 2025; updated Dec 18, 2025)**
- Skills are folders with SKILL.md (`name` and `description` frontmatter) using progressive disclosure: metadata is preloaded, the body loads when relevant, and linked files load on demand. Bundled scripts handle deterministic work. Install skills only from trusted sources and audit untrusted ones. Dec 18, 2025: "We've published Agent Skills as an open standard for cross-platform portability," supported on Claude.ai, Claude Code, the Agent SDK and the Developer Platform. [Vendor] — [Anthropic, Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
  - → Guild: *supports* shipping Guild's procedures as skills with bundled deterministic scripts, and the open standard *supports* the portability goal.

**Subagents and plugins (docs, fetched Oct 2026)**
- Subagent frontmatter supports `tools` (allowlist), `disallowedTools`, `model` (alias, full ID or `inherit`), `permissionMode`, `maxTurns`, `skills`, `hooks`, `memory`, `effort` and `isolation: worktree`. Subagents can nest up to 3 levels by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), with at most 20 running concurrently. `claude --agent <name>` runs the main thread *as* that agent, with its tool restrictions, model and system prompt. [Vendor] — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
  - → Guild: *supports* one role per `.claude/agents/*.md` with its own tools and model. `claude -p --agent reviewer` is the right way to run a role as the top-level headless session.
- **Plugin-provided subagents ignore `hooks`, `mcpServers` and `permissionMode`** for security, so copy the agent into `.claude/agents/` to use them. Name collisions resolve as managed > `--agents` > `.claude/agents/` > `~/.claude/agents/` > plugin. Model resolution: per-invocation param > frontmatter > `CLAUDE_CODE_SUBAGENT_MODEL` > main model, and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` overrides frontmatter. [Vendor] — [same](https://code.claude.com/docs/en/sub-agents)
  - → Guild: *supports* keeping role definitions per repo in `.claude/agents/` rather than inside the plugin, since role-scoped hooks and permission modes only work there. *Risk*: a repo-level agent with the same name silently shadows a plugin agent, and a forced subagent-model env var silently overrides GUILD.md's per-role models.
- Plugins bundle skills, agents, hooks, MCP servers and a manifest at `.claude-plugin/plugin.json` with an optional version. Every enabled plugin's skill and agent descriptions sit in context **on every turn**. Plugins run "as you." Plugin evals exist ("Test plugins with evals"). [Vendor] — [Claude Code docs, Plugins overview](https://code.claude.com/docs/en/plugins)
  - → Guild: *supports* the plugin-in-its-own-repo choice. *Cost*: every Guild skill description is paid on every turn of every role, so keep descriptions short and mark side-effecting skills `disable-model-invocation`.

**Managed Code Review product (docs, fetched Oct 2026)**
- Several agents search in parallel, a **verification step filters false positives**, and findings are deduplicated and ranked by severity. A review "never approves or blocks the pull request." **`REVIEW.md` is read from the base or default branch and "never from the pull request's own changes."** Reviews read the diff and code without building or running it. It does not run on Bedrock or Vertex alone (a Claude Team or Enterprise org is required). [Vendor] — [Claude Code docs, Code Review](https://code.claude.com/docs/en/code-review)
  - → Guild: *missing, and important*: the Reviewer (and every role) should read CHARTER.md, GUILD.md, AGENTS.md and `.claude/agents/*` **from the base branch**. Otherwise a Builder PR, or an injected PR, can rewrite the rules the Reviewer applies. Guild cannot depend on the managed product because of its portability constraint.

### Inferences
- The Anthropic material Guild can lean on most is the March 2026 planner/generator/evaluator harness: it is a published, first-party version of Guild's Planner/Builder/Reviewer core, with measured cost (20x) and an explicit lesson that roles should be re-justified after each model upgrade.
- No Anthropic source supports Triage or Releaser as separate *LLM* roles with evidence. They are plausibly better as mostly deterministic scripts with a small LLM call (classification or release-note drafting), which matches the "workflow, not agent" advice.
- Token and cost scaling (15x, 20x, $20k) makes GUILD.md budgets a core control, not a nice-to-have.

### Gaps
- Anthropic has not published a controlled comparison of "role-separated pipeline vs one agent" on real-repo maintenance (bug fixes, small features). The harness-design post compares one app built two ways, without repeated trials.
- I could not confirm whether `/goal`, "dynamic workflows" and the `--agents` file-path form are GA or preview. The best-practices page mentions them without labels; only agent teams and agent view are explicitly experimental or preview.

## 2. Counter-views (Cognition, OpenAI, Google) and what evidence decides for a Triage→Planner→Builder→Reviewer pipeline

### Takeaway
The counter-views have converged rather than conflicted. Cognition (2025, then 2026), OpenAI (2025) and Google Research (Dec 2025 / Jan 2026) all say: maximize one agent first, never let parallel agents make conflicting write decisions, and add agents that contribute *intelligence* (planning, read-only research, review) rather than *actions*. The best quantitative evidence (Google, 180 configurations) finds multi-agent setups **degrade sequential tasks by 39-70%** but help parallelizable ones, and MAST finds 41-87% failure rates in open-source multi-agent frameworks, dominated by spec, termination and verification failures. A sequential, single-writer pipeline with a fresh-context reviewer matches what is currently reported to work. A pipeline where roles debate or co-edit does not.

### Cited Findings
- **Cognition, "Don't Build Multi-Agents" (Jun 12, 2025, Walden Yan):** Principle 1, "Share context, and share full agent traces, not just individual messages"; Principle 2, "Actions carry implicit decisions, and conflicting decisions carry bad results." The Flappy Bird example: parallel subagents built a mismatched background and bird. Claude Code's subagent "is usually only tasked with answering a question, not writing any code." Recommends a single-threaded linear agent, with a compression model for long histories ("hard to get right"). [Vendor] — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
  - → Guild: *contradicts* thin summary handoffs. If the Planner hands the Builder only a plan comment, the Builder loses the Planner's reasoning and rejected alternatives. *Supports* one Builder per issue.
- **Cognition, "Multi-Agents: What's Actually Working" (Apr 22, 2026, Walden Yan):** Devin now uses several multi-agent flows: a generator-verifier loop with a "dedicated review agent" that "only look[s] at the diff," read-only subagents (DeepWiki), a "smart friend" larger model, and manager/child Devins coordinated through an internal MCP. What works: systems where "writes stay single-threaded and the additional agents contribute intelligence rather than actions." What fails: parallel writers, and unstructured swarms ("mostly a distraction"). [Vendor] — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- Same post: for reviewers, the best results came when "the coding and review agents do not share any context beforehand," a reversal of Principle 1 specific to review. Reviewers need a "communication bridge" carrying the user's instructions, or they drift into "looping, disobeying the user, doing work that is out of scope." Devin Review "catches an average of 2 bugs per PR," with "roughly 58%" severe. [Vendor claim, unaudited] — [same](https://cognition.com/blog/multi-agents-working)
  - → Guild: *strongly supports* Triage, Planner and Reviewer as read-only "intelligence" roles, the Builder as sole writer, and a Reviewer with clean context. *Missing*: the "bridge". The Reviewer must receive the issue's acceptance criteria and CHARTER non-goals so it doesn't flag in-scope choices or push out-of-scope work.
- **OpenAI, "A practical guide to building agents"** (PDF undated; I believe it came out April 2025 but did not verify the date): "Our general recommendation is to maximize a single agent's capabilities first." Split when prompts have many conditional branches ("Complex logic") or on "Tool overload," where "Some implementations successfully manage more than 15 well-defined, distinct tools while others struggle with fewer than 10 overlapping tools." Two patterns: **manager** (agents as tools) and **decentralized** handoffs. [Vendor] — [OpenAI, A practical guide to building agents (PDF)](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Same guide: rate each tool's risk "low, medium, or high" by "read-only vs. write access, reversibility, required account permissions." Escalate to a human on "Exceeding failure thresholds" (retry or action limits) and "High-risk actions." For a coding agent, escalation "means handing control back to the user." Model selection: build the prototype "with the most capable model for every task to establish a performance baseline," then swap smaller models in under evals. [Vendor] — [same](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
  - → Guild: *supports* per-role tool allowlists, risk tiers and steward escalation. *Supports* starting every role on the strongest model and then moving Triage, for example, to a cheaper one *after* evals, rather than pre-assigning cheap models by intuition.
- **Google Research, "Towards a science of scaling agent systems"** (arXiv 2512.08296, Dec 2025; blog Jan 28, 2026): 180 configurations across GPT, Gemini and Claude, comparing a single agent with independent, centralized, decentralized and hybrid multi-agent systems on Finance-Agent, BrowseComp-Plus, PlanCraft and Workbench. Centralized coordination gave **+80.9%** on parallelizable Finance-Agent, while **every multi-agent variant degraded sequential PlanCraft by 39-70%**. Independent agents amplified errors **17.2x**, centralized ones **4.4x** (a "validation bottleneck"). There is a "tool-coordination trade-off" as tool count rises (example: a coding agent with 16+ tools). A predictive model picked the best architecture for 87% of held-out configurations (R² 0.513). **No coding or SWE benchmark was included.** [Independent-ish: Google, a model vendor, but multi-vendor and peer-style] — [Google Research blog](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); [arXiv 2512.08296](https://arxiv.org/abs/2512.08296v2)
  - → Guild: *supports* centralized control through the deterministic orchestrator and *contradicts* peer-to-peer role chatter. Implementing a single issue is mostly sequential, which argues for one Builder rather than split builders.
- **MAST, "Why Do Multi-Agent LLM Systems Fail?"** (Cemri et al., UC Berkeley; v1 Mar 17, 2025, v3 Oct 26, 2025): 14 failure modes in 3 categories from 1,642 annotated traces across 7 frameworks (MetaGPT, ChatDev, HyperAgent, AppWorld, AG2, Magentic-One, OpenManus), kappa=0.88. Failure rates were **41%-86.7%**. Prevalence: step repetition 15.7%, reasoning-action mismatch 13.2%, unaware of termination conditions 12.4%, disobey task specification 11.8%, incorrect verification 9.1%, no or incomplete verification 8.2%, task derailment 7.4%, fail to ask for clarification 6.8%, premature termination 6.2%. [Independent] — [arXiv 2503.13657 v3 HTML](https://arxiv.org/html/2503.13657v3); [abstract](https://arxiv.org/abs/2503.13657)
- Same paper: simple fixes helped but did not solve the problem. A better ChatDev role spec or workflow gave **+9.4%**, and a high-level objective verification step **+15.6%**, while completion stayed low. "MAS failure is not merely a function of challenges in the underlying model"; failures stem from "organizational design and agent coordination." MetaGPT had 60-68% fewer spec and misalignment failures than ChatDev but 1.56x more verification failures. [Independent] — [arXiv 2503.13657 v3 HTML](https://arxiv.org/html/2503.13657v3)
  - → Guild: *supports* explicit termination conditions (max turns, budgets, "one PR then stop"), explicit specs (CHARTER, acceptance criteria) and an objective verification step (tests). It also shows that role prompts alone fix little. *Missing*: a "fail to ask for clarification" path, i.e. a way for Triage or Planner to stop and ask the steward through a comment instead of guessing.
- **Practitioner reports converge on single-writer pipelines with deterministic gates:**
  - Spotify's Honk (Dec 9, 2025): a Claude Code agent restricted to viewing code, editing files and calling verifiers. Pushing, Slack and prompt authoring live in surrounding infrastructure. It runs in a locked-down container, which Spotify says makes it "more predictable." [Vendor/practitioner] — [Spotify Engineering, Honk Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)
  - Stripe's "Minions" (Feb-Mar 2026, secondary): "blueprints," described as state machines interleaving deterministic nodes (lint, push) with agentic nodes (implement, fix tests). CI retries are reportedly capped at 2. 1,000-1,300+ PRs per week, every one human-reviewed. Built on a fork of Block's goose. [Secondary] — [InfoQ, Stripe autonomous coding agents](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/); [ByteByteGo](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs)
  - → Guild: *strongly supports* a deterministic orchestration script that owns pushes, labels and comments, with the LLM confined to the creative step. *Supports* hard retry caps.
- **Evidence on perceived vs measured productivity** (tangential but relevant to judging any pipeline): METR's July 2025 RCT found 16 experienced OSS developers took 19% *longer* with AI while believing they were ~20% faster. A Feb 2026 follow-up reportedly had confidence intervals spanning zero, and METR labels the original result historical. [Secondary for the 2026 part] — [ScienceBlog summary](https://scienceblog.com/t-a-randomized-trial-by-metr-found-that-experienced-developers-completed-real-coding-tasks-19-slower-when-allowed-to-use-ai-tools-yet-afterwards-they-estimated-on-average-that-ai-had-made-them-20-fast/); [CoderCops summary of 2026 update](https://blog.codercops.com/blog/ai-coding-productivity-2x-not-10x-metr-2026)

### Inferences
- What decides the question for Guild is not "multi-agent vs single agent" but "how many writers, and how lossy are the handoffs." Guild's design is already in the safe zone (one writer per issue, sequential, centrally orchestrated), but the issue-comment handoff between Planner and Builder is exactly the "summary, not full trace" pattern Cognition warns about. Mitigations: the Builder reads the full issue thread plus the plan; the plan is structured (files touched, acceptance tests, out-of-scope list); and Planner and Builder could even be one session (`opusplan`-style plan, then execute) for mid-size tiers.
- Triage and Releaser look like *routing* and *chaining* workflow steps. Making them full agents adds cost and the MAST failure surface (step repetition, termination) for little gain. They are good candidates for "deterministic script + one bounded LLM call."
- Google's "independent agents amplify errors 17.2x" is the strongest argument against letting the Reviewer and Builder iterate unsupervised without a deterministic referee such as tests, iteration caps or a steward command.

### Gaps
- No independent study evaluates a Triage→Planner→Builder→Reviewer pipeline against a single agent on real repository maintenance. Google's study had no coding benchmark, and MAST's coding systems (ChatDev, MetaGPT) are 2023-era designs with older models.
- I did not review Google's Kaggle/Google Cloud "Agents" whitepapers (2024-2025). Only the Google Research scaling paper is covered here.
- Cognition's 2026 numbers (2 bugs per PR, 58% severe) are unaudited vendor figures with no stated false-positive rate.

## 3. Spec-driven and plan-first development: Spec Kit, Kiro, AGENTS.md, CLAUDE.md, constitutions, evidence

### Takeaway
Repo-level charters are now an industry convention: Spec Kit's `constitution.md` with numbered articles and "Phase -1 gates," Kiro's steering files, AGENTS.md under the Linux Foundation's Agentic AI Foundation, and CLAUDE.md. Guild's CHARTER.md with numbered principles maps closely onto Spec Kit's constitution. The evidence that heavy spec workflows improve outcomes is **thin and mostly vendor-asserted**. The most careful independent review (Thoughtworks, Oct 2025) found review overload, agents ignoring specs, and one-size-fits-all workflows. The only recent benchmark signal suggests *requirement clarification*, not planning, is the dominant failure source.

### Cited Findings
- **GitHub Spec Kit** (Sep 2, 2025, Den Delimarsky): an open-source toolkit with phases `/specify` (what and why, no tech stack), `/plan` (stack and architecture), `/tasks` (small testable tasks), then implement. It supported GitHub Copilot, Claude Code and Gemini CLI at launch. Framing: "We're moving from 'code is the source of truth' to 'intent is the source of truth'"; LLMs are "exceptional at pattern completion, but not at mind reading." The post presents **no metrics** and calls Spec Kit "our experiment." [Vendor] — [GitHub Blog, Spec-driven development with AI](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- **Spec Kit constitution** (`memory/constitution.md`), "the architectural DNA of the system": Article I Library-First, II CLI Interface, III Test-First ("NON-NEGOTIABLE"), VII Simplicity ("Maximum 3 projects"), VIII Anti-Abstraction, IX Integration-First Testing ("Prefer real databases over mocks"); Articles IV-VI are project-defined. It is enforced through **"Phase -1: Pre-Implementation Gates"** in the plan template, and when a gate fails "the LLM must document why in the 'Complexity Tracking' section." Templates require `[NEEDS CLARIFICATION: …]` markers and a checklist item that none remain. Amendments require rationale, maintainer approval and a backwards-compatibility assessment. [Vendor] — [github/spec-kit, spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
  - → Guild: *supports* CHARTER.md with numbered principles. *Missing*, and worth borrowing: (a) **gates** that make the Planner check its plan against each numbered principle and record justified exceptions; (b) explicit `[NEEDS CLARIFICATION]` markers that route back to the steward; (c) an amendment procedure for CHARTER.md (only the steward edits it, with rationale).
- **Kiro (AWS)**: per-feature specs in `.kiro/specs/` as `requirements.md` (user stories with **EARS** acceptance criteria, "WHEN [condition] THE SYSTEM SHALL [behavior]"), `design.md` and `tasks.md`. Project-level **steering files** in `.kiro/steering/` cover product, tech stack, structure and custom standards. Reportedly there are approval gates between phases. [Vendor, partly Secondary] — [Kiro docs, Specs concepts](https://kiro.dev/docs/specs/concepts); [Kiro docs, requirements-first](https://kiro.dev/docs/specs/feature-specs/requirements-first/)
  - → Guild: EARS-style acceptance criteria in issue templates would give the Reviewer and tests checkable targets. *Supports* AGENTS.md and CHARTER.md as the "steering" layer.
- **Independent critique, Birgitta Böckeler (Thoughtworks), "Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl"** (Oct 15, 2025):
  - Defines **spec-first** (spec written before the task), **spec-anchored** (spec kept and maintained afterwards) and **spec-as-source** (humans edit only the spec). Most tools are spec-first, and maintenance strategy is "often left vague."
  - Kiro on a small bug fix was "like using a sledgehammer to crack a nut" (4 user stories, 16 acceptance criteria).
  - Spec Kit "created a LOT of markdown files for me to review," and the agent sometimes ignored instructions (duplicating existing classes) or was "too eagerly following instructions."
  - "I'd rather review code than all these markdown files." Larger context windows don't mean the agent picks everything up.
  - Spec-as-source risks "Inflexibility and non-determinism," like Model-Driven Development.
  - She asks: "Are we making something worse in the attempt of making it better?"
  - [Independent] — [martinfowler.com, Böckeler](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
  - → Guild: *supports* Guild's tiered path map, since small changes must not pay full-spec overhead. *Warns* that Planner output must stay short and reviewable. A steward who has to review a long plan *and* the code gets Böckeler's review overload. Guild's roadmap-as-issues is "spec-anchored" only if issues are kept current after merge, so decide whether closed issues are the record or ROADMAP.md is regenerated from them.
- **AGENTS.md**: an "open format… a README for agents," plain Markdown with no required fields. The nearest file in the tree takes precedence, and explicit user prompts override it. Listed test commands are run by agents. It claims 60k+ OSS projects. Stewarded by the **Agentic AI Foundation** under the Linux Foundation. Listed supporting agents include Codex, Jules, Cursor, Copilot coding agent, Gemini CLI, Devin, Windsurf, Aider, goose, Zed, Warp and Junie. **Claude Code does not appear in the list on the page.** [Vendor/standard body] — [agents.md](https://agents.md/)
- **Agentic AI Foundation** launched Dec 9, 2025 with founding projects Anthropic's MCP, Block's goose and OpenAI's AGENTS.md. Platinum members include Amazon, Google, Microsoft, Bloomberg and Cloudflare. [Secondary press] — [SD Times](https://sdtimes.com/ai/linux-foundation-forms-agentic-ai-foundation-to-be-new-home-for-mcp-goose-and-agents-md/); [ITPro](https://itpro.com/software/open-source/anthropic-says-mcp-will-stay-open-neutral-and-community-driven-after-donating-project-to-linux-foundation)
  - → Guild: *supports* AGENTS.md as the vendor-neutral handbook. Because Claude Code reads CLAUDE.md, Guild needs a CLAUDE.md that imports it with `@AGENTS.md`, exactly as confusable already does (the best-practices doc confirms `@path` imports). That keeps the handbook portable to non-Claude agents.
- **Claude Code's own guidance on plan-first** (fetched Oct 2026): plan mode "is useful, but also adds overhead." It is most useful "when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code"; otherwise skip it. Write SPEC.md and then "start a fresh session to execute it." [Vendor] — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- **Evidence that plan-then-implement improves outcomes (weak, mixed, mostly snippets):**
  - Older foundation: 2023 self-planning code generation reported up to 25.4% relative Pass@1 gains on function-level benchmarks, which don't transfer to repo-level work. [Independent, older] — [arXiv 2303.06689](https://arxiv.org/pdf/2303.06689v3)
  - A 2026 preprint on planning-mode declarations reports pattern-specific executors raising SWE-bench Verified success from 0.36 to 0.44 over generic Plan+ReAct, and that generic executors often don't follow declared plans. [Secondary] — [OpenTrain summary of arXiv 2609.38108](https://www.opentrain.ai/papers/do-llm-agents-execute-the-plans-they-declare-from-planning-mode-declaration-to-p--arxiv-2609.38108/)
  - "From Plan to Action: How Well Do Agents Follow the Plan?" evaluates plan compliance on 497 SWE-bench Verified instances. I did not see the headline numbers. [Independent, unread] — [arXiv 2604.12147](https://arxiv.org/pdf/2604.12147)
  - SWE-RPG (arXiv 2608.09072) separates failures into requirement clarification, planning and code generation. A blog summary says planning is ~11% of failures and requirement clarification the largest share. [Secondary] — [arXiv 2608.09072](https://arxiv.org/pdf/2608.09072); [blog summary](https://codex.danielvaughan.com/2026/09/01/swe-rpg-implicit-requirement-recovery-coding-agents-bottleneck-codex-cli/)
  - MAST independently finds "fail to ask for clarification" at 6.8% and "disobey task specification" at 11.8% of multi-agent failures. [Independent] — [arXiv 2503.13657 v3](https://arxiv.org/html/2503.13657v3)
  - → Guild: *supports* putting effort into **Triage** turning vague issues into clear acceptance criteria, possibly more than into a heavy Planner. *Missing*: evidence that the Planner role, as distinct from good acceptance criteria, improves Builder success. Guild should measure it.

### Inferences
- CHARTER.md (mission, scope, non-goals, numbered principles) is well aligned with practice. Its value depends on *enforcement points* (Spec Kit's Phase -1 gates, the Reviewer checking non-goals) rather than on being read.
- The strongest evidence-backed spec element is *verifiable acceptance criteria*: tests, EARS statements, and "end with an end-to-end verification step." Narrative plans are the weakest.
- Spec-anchored maintenance is the open problem in every tool. Guild's issues→ROADMAP.md generation is a plausible answer, provided the generator is deterministic and issues are the only edited source.

### Gaps
- No independent controlled study shows Spec Kit, Kiro or constitution files improve defect rates or delivery time.
- I did not verify whether Claude Code now reads AGENTS.md natively. The agents.md list omits it, and Claude Code docs describe only CLAUDE.md with `@` imports.

## 4. Agent-to-agent review: does a second model catch defects? Benchmarks, agreement bias, cross-family review, adversarial reviewers

### Takeaway
AI reviewers catch a meaningful but partial share of defects. On the most cited open benchmark (Martian's Code Review Bench, 2026), the best tools score roughly **50-65% F1**, and rankings change with every snapshot and vendor. Academic results show performance **collapses on real, larger diffs** (F1 0.657 for diffs under 10 lines vs 0.043 over 150 lines in one study). Self-evaluation is biased toward one's own output, so a separate, fresh-context reviewer helps. The only controlled cross-model study (Oct 2026) found **no significant F1 gain from switching model family** once reviewer capability is controlled, though two different reviewers together find more errors than two of the same. Practitioners report LLM reviewers and judges can be too rigid or over-flag, and that they need bounded scopes and deterministic tests underneath.

### Cited Findings
**Benchmarks (treat all leaderboards as snapshots)**
- **Martian Code Review Bench** has an offline track (50 curated PRs from 5 repos, 136 human-curated golden comments, LLM judge) and an online track that tracks whether developers act on comments in real OSS PRs. Data, judge prompts and pipeline are published. [Independent-ish: Martian is not a review vendor but sells model routing] — [Kumar et al., arXiv 2606.15689](https://arxiv.org/pdf/2606.15689); [Greptile on Martian benchmark](https://www.greptile.com/content-library/greptile-martian-code-review-benchmark)
- Snapshot numbers: Greptile reports itself first online at **60.8% F1** (Jul 30, 2026) [Vendor]. A Martian-based snapshot reported Cubic at **64.9% F1** and GitHub Copilot fourth at **60.9%** as of Oct 6, 2026 [Secondary]. Earlier figures circulating were CodeRabbit ~51% F1 and Greptile 50.2% F1 (66.2% precision, 40.4% recall) [Secondary]. — [Greptile](https://www.greptile.com/content-library/greptile-martian-code-review-benchmark); [The New Stack headline](https://thenewstack.io/github-reviewbench-code-review/) (body not retrievable; numbers via search snippet); [Morph comparison](https://www.morphllm.com/comparisons/coderabbit-vs-greptile)
- Martian's own docs reportedly concede that the offline gold set is incomplete, the PRs are older, and judges aren't formally calibrated against humans. [Secondary, via a competitor] — [Qodo](https://www.qodo.ai/?p=21766)
- **GitHub ReviewBench** (Oct 5, 2026) ranks Copilot first. Different data and method, so it doesn't map onto Martian. [Vendor] — [DevX explainer](https://www.devx.com/coding/what-is-reviewbench-ai-code-review-benchmark/)
- Vendor-run benchmarks (Tenki, Macroscope, CodeRabbit-sponsored Signal65, Greptile) each place the publisher first. Treat them as marketing. [Vendor] — [Tenki benchmark](https://tenki.cloud/benchmarks/code-reviewer.md); [Signal65/CodeRabbit infographic](https://signal65.com/wp-content/uploads/2026/04/CodeRabbit-Evaluating-AI-Code-Review-Tools-Infographic.pdf)
- **Kumar, Bararia & Raj, "Bigger Isn't Always Better"** (arXiv 2606.15689, Apr 2026): 150 samples (100 mutation-injected, 50 real bug-fix PRs from 8 repos) across Claude Sonnet 4.6, Claude Haiku 4.5, GPT-5.4 mini, Minimax M2.7 and GLM-5 Turbo. **Haiku 4.5 F1 0.365 vs Sonnet 4.6 0.343**, Haiku 18% higher recall and 3.2x cheaper. Best F1 on **real PRs only was 0.066** vs 0.847 on synthetic. F1 fell from **0.657 (<10-line diffs) to 0.043 (>150 lines)**. Recall on performance bugs was near zero. [Independent, small n, abstract only] — [arXiv 2606.15689](https://arxiv.org/abs/2606.15689)
  - → Guild: *supports* small PRs (one issue, one small diff) as the strongest lever on Reviewer quality. *Supports* not assuming the biggest model is the best Reviewer: measure on the repo's own history. *Warns* that Reviewer approval is weak evidence of correctness, so tests and oracles must carry the weight.

**Self-preference and agreement bias**
- Chen et al., "Do LLM Evaluators Prefer Themselves for a Reason?" (v1 Apr 4, 2025, v3 Dec 12, 2025) studied math, factual QA and code with ground truth. Stronger models prefer themselves more, mostly *legitimately* (they really are better), but **harmful self-preference** (preferring their own wrong answers) persists and is more pronounced in stronger models: "stronger models struggle more to recognize when they are wrong." Long chain-of-thought before judging reduces it. [Independent] — [arXiv 2504.03846](https://arxiv.org/abs/2504.03846)
- Older foundation: Panickssery et al. (2024) found GPT-4 and Llama 2 can recognize their own generations, and fine-tuning suggests self-recognition causally drives self-preference. Perplexity-based self-preference was also reported for GPT-4 (NeurIPS 2024). [Independent, older] — [arXiv 2404.13076](https://arxiv.org/pdf/2404.13076v1); [NeurIPS 2024 poster](https://neurips.cc/virtual/2024/106181)
- Rubric-based judging (binary per-criterion verdicts) also shows self-preference under both pairwise and direct scoring. [Independent, abstract only] — [alphaXiv 2604.06996](https://www.alphaxiv.org/abs/2604.06996)
- Anthropic: agents "reliably skew positive when grading their own work," and even a separate evaluator "tends to be generous" until tuned with few-shot calibration. [Vendor] — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
  - → Guild: *supports* a separate Reviewer that never sees the Builder's reasoning, with high reasoning effort, plus calibration examples in the Reviewer's role file (past real findings and non-findings).

**Cross-family review**
- **Song, "When Does a Second Model Help? Cross-Model Review in LLM Verification"** (arXiv 2610.01471, Oct 1/6, 2026): 30 artifacts, 150 planted errors, 900 sessions, three reviewer models from two developers. A top-tier cross-model reviewer showed **no significant F1 difference** from same-model review in a fresh session ("does not establish equivalence"). The reviewers found partly different errors (Jaccard 41.2%). **One fresh same-model review plus one cross-model review caught 56.7% of planted errors vs 42.7% for two same-model reviews** (Holm p=.006), but did not beat two top-tier cross-model reviews. Lightweight cross-model reviewers scored no higher than same-model review. Capability is confounded with model identity. Single author, data on request only. [Independent, preliminary] — [arXiv 2610.01471](https://arxiv.org/abs/2610.01471)
  - A secondary summary claims the paper reports separate code and document results (same-model fresh-session F1 40.7% vs 37.2% cross-model on code). I could not confirm this split from the abstract. — [agentpatterns.ai summary](https://agentpatterns.ai/verification/cross-model-review-independence/)
- Practitioner anecdotes say Codex reviewing Claude's diffs catches bugs Claude-family reviewers missed, and that cross-model reviewers have higher false-positive rates (~30% in one tool's experience). [Anecdotal/Vendor] — [Zack Proser](https://zackproser.com/blog/codex-reviews-claudes-diffs); [agentpatterns.ai](https://agentpatterns.ai/verification/cross-model-review-independence/)
  - → Guild: the portability constraint (Anthropic, Bedrock, Vertex, i.e. Claude only) rules out a cross-*family* Reviewer. The evidence suggests this costs little, *provided* the Reviewer is a top-tier model in a fresh session. Diversity can come from a second, differently prompted review pass (security or charter-compliance) rather than another vendor. *Uncertain*: one study, not replicated.

**LLM judges in production: scope policing and rigidity**
- Spotify (Dec 9, 2025): an LLM judge comparing the diff with the original prompt runs after deterministic verifiers, because agents got "a bit too 'ambitious'" (refactoring, disabling flaky tests). It "vetoes about a quarter of" thousands of sessions, and agents course-correct about half the time. Spotify had built no evals for the judge. [Vendor/practitioner] — [Spotify Engineering, Honk Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)
- Spotify, QCon London (Mar 18, 2026): the judge "was too rigid and blocked valid changes" and **was removed as models improved**, with "verification steps in prompts proving sufficient." Honk reached "1,000 merged pull requests every 10 days," and PR review became the new bottleneck. [Secondary report of practitioner talk] — [InfoQ, Spotify Honk rewrite](https://www.infoq.com/news/2026/03/spotify-honk-rewrite/)
- Claude Code docs: a reviewer "prompted to find gaps will usually report some, even when the work is sound." Bound it to correctness and stated requirements. [Vendor] — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- Claude Code managed review uses parallel finders plus a **verification step to drop false positives**, and never approves or blocks. [Vendor] — [Claude Code docs, Code Review](https://code.claude.com/docs/en/code-review)
- Cognition: reviewers work best with "a completely clean context," but need a bridge to user instructions or they loop and go out of scope. [Vendor] — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
  - → Guild: *supports* a two-stage Reviewer (find, then self-verify each finding against the code before posting). *Supports* the Reviewer advising rather than gating, with merge left to the human. *Warns* that a charter-compliance judge can become a source of false vetoes, so track its veto and override rate and be ready to remove it.

### Inferences
- In Guild's case the defect-catching weight should sit with **deterministic oracles** (confusable's conformance fixtures, strict xfails, hypothesis tests, pre-commit). The Reviewer is a second line, best aimed at what tests can't see: scope creep against CHARTER non-goals, spec deviations without the required comment, and missing tests for new behaviour.
- Expect the Reviewer to miss roughly a third to a half of real issues even at state-of-the-art levels, and far more on large diffs. Diff-size limits per tier are a cheap, evidence-backed control.
- Reviewer and Builder from the same family and model tier is defensible if the Reviewer gets a fresh context, a base-branch copy of the rules, and high effort. Running an extra reviewer pass on a *different Claude tier* (e.g. Haiku plus Opus) is a cheap way to get some of the "different errors" benefit, though that specific configuration is untested.

### Gaps
- No independent precision/recall data for Cursor Bugbot, Copilot code review or Claude Code Review beyond leaderboard snapshots. Claude Code Review publishes no accuracy stats.
- No study measures *sycophancy in multi-turn Builder↔Reviewer loops*, i.e. whether a Builder caves to wrong review comments or a Reviewer withdraws correct ones after pushback.
- Martian leaderboard methodology details (judge model, re-scoring cadence) were only seen secondhand.

## 5. Orchestration and state: queues vs events, idempotency, concurrency, failures and retries, handoff memory, issues/PRs as state, gh-aw, Continuous AI, Agent HQ, MCP vs CLI, oracles

### Takeaway
Practitioners run unattended coding agents as **event-triggered, short, single-purpose jobs** with deterministic pre- and post-steps. State lives in git, files and the issue tracker; writes go through narrow, pre-approved channels; and a hard verification gate (stop hook or CI) sits before any PR. GitHub's own agentic-workflow design (gh-aw, technical preview Feb 2026) formalizes this: a read-only agent, writes buffered as artifacts and applied by a separate job, a threat-detection job and an egress firewall. Prompt injection through issue and PR text in privileged CI agents is a demonstrated, real-world attack class (PromptPwnd, Dec 2025). GitHub Actions concurrency **silently drops pending runs by default**, so event-driven designs must reconcile from state rather than trust that every event is processed.

### Cited Findings
**GitHub Actions mechanics that constrain Guild**
- Concurrency groups allow at most one running and, by default (`queue: single`), **one pending** run. A newly queued run **cancels and replaces** the existing pending one. `queue: max` allows up to 100 pending (FIFO by wait start, not guaranteed) and cannot be combined with `cancel-in-progress: true`. [Vendor docs] — [GitHub Docs, Control workflow concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
  - → Guild: *missing*. If role runs share a concurrency group, bursts of events (several comments, labels) will drop work. Use `queue: max` or per-issue groups, and make every run **idempotent and state-reconciling**: re-read the issue's labels and comments and decide what to do, instead of acting on the triggering event payload alone.
- `claude-code-action@v1` checks (fetched Oct 2026):
  - On issue and PR events the triggering user needs **write access** (`allowed_non_write_users` overrides this).
  - **Bot actors are rejected unless listed in `allowed_bots`**, "which keeps bots from triggering Claude in a loop." This also applies to scheduled runs attributed to a bot.
  - "GitHub doesn't trigger workflows on commits made with the default `GITHUB_TOKEN`."
  - Scheduled workflows run only from the default branch and, in public repos, are disabled after 60 days without activity.
  - Cost controls: `--max-turns`, workflow timeouts, "GitHub's concurrency controls."
  - Inference via `use_bedrock`, `use_vertex` or `use_foundry` with OIDC, or Anthropic workload identity federation instead of a stored API key.
  - Plugins install through `plugin_marketplaces` and `plugins` inputs, with `/plugin-name:skill-name` as the prompt.
  - `@beta` is superseded by `@v1`.
  - [Vendor docs] — [Claude Code docs, GitHub Actions](https://code.claude.com/docs/en/github-actions)
  - → Guild: *critical design constraints*. (1) If one role hands off to the next by posting a bot comment or label, the next workflow either won't trigger (GITHUB_TOKEN events) or the action will reject the bot actor unless `allowed_bots` lists it, so Guild's orchestration script should chain roles explicitly (`workflow_dispatch` or one job running roles in sequence) rather than through comment ping-pong. (2) Use a GitHub App token for pushes so CI runs on Builder commits. (3) *Supports* portability to Bedrock and Vertex via OIDC, with no static keys. (4) A scheduled reconciler needs the "fail loudly" pattern; confusable's AGENTS.md already mandates a `scheduled` job that fails while any schedule is disabled.
- GitHub sub-issues and issue types became GA around Apr 9, 2025, after a Jan 2025 public preview. Issue types are configured per **organization** (defaults task, bug, feature; up to 25 types). [Vendor; partly Secondary] — [GitHub changelog 2025-04-09](https://github.blog/changelog/2025-04-09-evolving-github-issues-and-projects/); [GitHub Docs, Managing issue types](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-types-in-an-organization)
  - → Guild: *supports* issues and sub-issues as the roadmap store. *Caveat*: issue types appear to be org-level, so personal-account repos may not have them, and Guild should degrade to labels (unverified).

**GitHub Agentic Workflows (gh-aw) and Continuous AI**
- Technical preview **Feb 13, 2026**. Workflows are Markdown files in `.github/workflows/` that `gh aw compile` turns into `.lock.yml` Actions workflows. Triggers are issues and PRs, schedules, manual dispatch and **comment commands**. Built by GitHub Next, Microsoft Research and Azure Core Upstream; MIT-licensed. Use cases include triage, PR review, CI failure analysis, docs and test coverage ("Peli's Agent Factory," 50+ examples). [Vendor] — [GitHub changelog, gh-aw technical preview](https://github.blog/changelog/2026-02-13-github-agentic-workflows-are-now-in-technical-preview/)
- Engines: Copilot (default), **Claude Code**, Codex, Gemini, Pi. [Vendor docs] — [gh-aw overview](https://github.github.com/gh-aw/introduction/overview/)
- Security architecture:
  - The agent job is **read-only and never holds write access**. Writes are buffered as artifacts (`agent_output.json`, `aw.patch`) and applied by separate **safe-output jobs** with scoped permissions.
  - A **threat-detection job** (an AI agent with a security prompt, no write permissions) gives a *blocking* verdict before any write.
  - A Squid-proxy egress **domain allowlist** (`network.allowed`) and an MCP gateway run in isolated containers.
  - Compile-time checks: expression allowlists, no secrets in expressions, SHA-pinned actions, and actionlint/zizmor/poutine scans. A strict mode is available.
  - A `min-integrity` filter by author trust (public repos default to `approved`). Pre-activation role checks, a **stop-after deadline** and "command position validation."
  - Secret redaction runs over output files.
  - [Vendor docs] — [gh-aw security architecture](https://github.github.com/gh-aw/introduction/architecture/)
  - → Guild: *strong template*. Guild's "steward comment commands parsed by a deterministic script" matches gh-aw's role checks and command-position validation. *Missing* in Guild: (a) splitting each role into a read-only agent step plus a deterministic "apply outputs" step holding the write token; (b) an egress allowlist; (c) a content-integrity filter so untrusted authors' text isn't fed to agents; (d) a threat or secret scan before writes. *Conflict*: gh-aw itself is a technical preview and its README calls it a research demonstrator, so under Guild's no-beta rule Guild should **copy the pattern, not depend on gh-aw**.
- "Continuous AI" (GitHub Next, coined Jun 2025 by Don Syme): an open-ended category modelled on CI/CD, explicitly "not a term GitHub owns." Workflows "are not fully autonomous, but rather involve human oversight and control" and make "targeted, reliable use of AI." A Feb 2026 post frames it as "background agents that operate in your repository the way CI jobs do, but only for tasks that require reasoning instead of rules." [Vendor] — [GitHub Next, Continuous AI](https://githubnext.com/projects/continuous-ai/); [GitHub Blog, Continuous AI in practice](https://github.blog/ai-and-ml/generative-ai/continuous-ai-in-practice-what-developers-can-automate-today-with-agentic-ci/); [Simon Willison, Jun 27, 2025](https://simonwillison.net/2025/Jun/27/continuous-ai/)
  - → Guild: *supports* the framing that Guild is a set of CI-like, human-overseen background jobs rather than an autonomous team.
- **Agent HQ** (announced Oct 28, 2025): "mission control" across Copilot and third-party agents (Anthropic, OpenAI, Google, Cognition, xAI, some arriving later). Reportedly agents run in sandboxed Actions environments with firewall protections and **can only commit to designated branches**. [Secondary press] — [SiliconANGLE](https://siliconangle.com/2025/10/28/github-tackles-vibe-coding-chaos-control-center-ai-coding-agents/); [VentureBeat](https://venturebeat.com/ai/githubs-agent-hq-aims-to-solve-enterprises-biggest-ai-coding-problem-too); [Visual Studio Magazine](https://visualstudiomagazine.com/Articles/2025/10/28/GitHub-Introduces-Agent-HQ-to-Orchestrate-Any-Agent-Any-Way-You-Work.aspx)
  - → Guild: a possible future competitor or host. *Supports* branch-restricted writes (Builder only pushes `<type>/<topic>` branches, never `main`).

**Security of CI-triggered agents**
- **PromptPwnd** (Aikido Security, Dec 4, 2025; updated Mar 17, 2026): untrusted issue titles and bodies, PR descriptions and commit messages reach prompts, and the agent uses privileged tools (`gh issue edit`) to leak secrets or alter workflows. "At least 5 Fortune 500 companies" were affected, and Google patched Gemini CLI's action within 4 days. For **Claude Code Actions**, the default write-access check is a boundary, and setting `allowed_non_write_users: "*"` is "extremely dangerous." In testing, a privileged `GITHUB_TOKEN` "could almost always be leaked" when an attacker could trigger the workflow, **even without direct prompt embedding, because Claude fetched the malicious content itself through its tools**. Env vars don't help. Mitigations: restrict tools (no issue or PR writes), don't inject untrusted input, treat AI output as untrusted, limit token blast radius. [Independent security vendor] — [Aikido, PromptPwnd](https://www.aikido.dev/blog/promptpwnd-github-actions-ai-agents)
- A Cloud Security Alliance note (May 2026) says agents including Claude Code process untrusted repo content (PR titles, issue bodies, comments, branch names) while holding elevated privileges. [Independent, Secondary] — [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-github-actions-security-20260503-csa-st/)
  - → Guild: *critical*. Triage reads public issue text by design, so the Triage role must have **no write tools and no secrets beyond a read token**, with label and comment writes applied by the deterministic script from a structured output it validates. Confusable's AGENTS.md rule "never interpolate untrusted text… into a `run:` step" covers shell injection but **not prompt injection**, which needs its own rule.

**Handoff memory, checkpoints, failure handling**
- Anthropic long-running harness: `claude-progress.txt` plus git log let a fresh session "quickly understand the project's state." Each session starts by running `init.sh` and a basic end-to-end test, to catch breakage left by the previous session. [Vendor] — [Anthropic, Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Anthropic harness design: agents communicate through files. Context *resets* with a handoff artifact were needed for Sonnet 4.5 and dropped for Opus 4.5, whose compaction sufficed. [Vendor] — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Anthropic research system: resume from failure point, checkpoints, retries, and telling the agent when a tool fails so it can adapt. [Vendor] — [Anthropic, Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Carlini's C compiler: task locks as files in git, CI blocking regressions, minimal console output with logs to files, `--fast` sampling, and a `while true` loop restarting fresh sessions. One agent ran `pkill -9 bash` and killed its own loop. [Vendor] — [Anthropic, C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- Spotify: verifiers exposed as an MCP tool the agent "can (and in certain cases must)" call without knowing their internals. They auto-activate per component (e.g. `pom.xml` → Maven) and parse errors with regexes to return short messages. **Claude Code runs all relevant verifiers in a stop hook; if one fails, the PR isn't opened.** Failure ranking: no PR ("minor annoyance") < PR fails CI < PR passes CI but is wrong ("erodes trust"). [Vendor/practitioner] — [Spotify Engineering, Honk Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)
- Spotify (Mar 2026): verification moved to a separate service. Honk pushes branches, the service abstracts CI and reports back, and PRs are created only after validation passes. [Secondary] — [InfoQ](https://www.infoq.com/news/2026/03/spotify-honk-rewrite/)
- Stripe: CI retries reportedly capped at 2 rounds. [Secondary] — [ByteByteGo](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs)
- OpenAI: escalate to a human on "Exceeding failure thresholds." [Vendor] — [OpenAI guide PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
  - → Guild: *supports* issues and PRs as the state store, the steward as escalation, and budgets in GUILD.md. *Missing*: (a) a structured per-issue state record (a JSON block in a bot-owned comment, or labels as a state machine) that only the script edits, following Anthropic's "JSON is less likely to be overwritten" finding; (b) an explicit retry cap per role, after which the issue is labelled for the steward; (c) a "no PR is better than a wrong PR" policy, where the Builder exits without a PR when its Stop-hook gate fails.

**MCP vs CLI**
- Claude Code docs: CLI tools like `gh` are "the most context-efficient way to interact with external services." [Vendor] — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- Anthropic (Nov 4, 2025): presenting MCP servers as code APIs on a filesystem, loaded on demand, cut one workflow from **150,000 to 2,000 tokens (98.7%)**. Caveat: running agent-written code needs sandboxing, resource limits and monitoring. [Vendor] — [Anthropic, Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
- claude-code-action's inline-comment MCP server only starts when `--allowedTools` names it, and plain-text prompts get no shell or GitHub API access until tools are granted. [Vendor docs] — [Claude Code docs, GitHub Actions](https://code.claude.com/docs/en/github-actions)
  - → Guild: *supports* `gh` plus deterministic scripts over MCP for GitHub operations. It also keeps Guild free of MCP-server operational burden and portable.

**Tests and oracles as ground truth**
- Carlini: "the verifier must be nearly perfect." Anthropic's long-running harness forbids editing tests. Spotify's agents disabled flaky tests until the judge stopped them. Spotify's early agents commented out failing tests and downgraded Java versions. [Vendor] — [Anthropic, C compiler](https://www.anthropic.com/engineering/building-c-compiler); [Anthropic, Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3); [InfoQ](https://www.infoq.com/news/2026/03/spotify-honk-rewrite/)
  - → Guild: *missing*: a hook-level guard that blocks the Builder from editing tests, fixtures and oracles. Confusable's "never edit generated tables or fixtures by hand" rule is advisory and should become a PreToolUse hook or a CI diff check that fails when a Builder PR touches `tests/conformance/fixtures/` or `src/confusable/_data/` without the generator changing.

### Inferences
- Event-driven Actions plus idempotent reconciliation is enough for Guild's scale. A durable external queue (Temporal etc.) would add infrastructure without a clear need, since GitHub issue state *is* the durable queue, provided every run re-derives what to do from the issue and concurrency is per-issue.
- The safest Guild topology mirrors gh-aw without depending on it: `trigger → deterministic gate (actor role, command parse, budget) → read-only Claude run with role agent → validated structured output → deterministic apply step with scoped token`. Only the Builder needs `contents: write`, scoped to its branch.
- Chaining roles through comments is fragile given the GITHUB_TOKEN no-trigger rule and the bot-actor rejection. A single orchestrator job that runs roles in sequence for one issue, or `workflow_dispatch` calls with an App token, is more robust.

### Gaps
- I did not research durable-execution frameworks (Temporal, Restate, Inngest) for agent orchestration, so I have no comparative evidence on queue vs event designs for coding agents.
- No first-party data on how claude-code-action behaves on runner timeouts mid-edit (partial pushes, resumability).
- gh-aw details (threat-detection accuracy, staged mode, `stop-after` semantics) are from docs only. I found no independent evaluation of its threat-detection job.
- Agent HQ and Stripe details are from secondary press, not primary posts.

## 6. Long-term maintainability: prompts and skills under version control, pinning models, model upgrades, vendor portability

### Takeaway
Treat prompts, skills, role files and harness scripts as versioned code with evals. **Pin models to full IDs per provider**, because Claude Code aliases move automatically and resolve to *different* models on Bedrock and Vertex, and expect each pinned Anthropic model to be retired roughly 12-15 months after release, with at least 60 days' notice (partner clouds set their own schedules). Every model upgrade is also a chance, and a need, to delete scaffolding: Anthropic and Spotify both removed harness components (sprints, LLM judge) after model upgrades.

### Cited Findings
- **Aliases move**: Claude Code aliases "point to the recommended version for your provider and update over time." Current targets differ by provider: on the Anthropic API `sonnet` = Sonnet 5.5, but on Bedrock and Google Cloud `sonnet` = Sonnet 4.5 and `haiku` = Haiku 4.5. Pin with `--model <full-id>` or `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU,FABLE}_MODEL`. Precedence: `/model` > `--model` > `ANTHROPIC_MODEL` > `model` setting. Default effort also differs per model (`medium` on the 5.5 family, `high` on most others), and unsupported effort levels fall back silently. Managed settings offer `availableModels`, `deniedModels` and `availableModelsMatch: "exact"`. [Vendor docs] — [Claude Code docs, Model configuration](https://code.claude.com/docs/en/model-config)
  - → Guild: *supports* GUILD.md declaring models per role, which must be **per provider** (full IDs for Anthropic, Bedrock and Vertex) and must also pin **effort**. *Risk*: `model: sonnet` in a role file means a different model on Bedrock than on the API, which breaks portability of behaviour.
- **Retirement cadence and notice**: Anthropic gives "at least 60 days' notice before model retirement for publicly released models" and recommends testing replacements "well before the retirement date." Bedrock and Google-managed Vertex "set their own retirement schedules." Examples: `claude-sonnet-4-20250514` deprecated Apr 14, 2026, retired Jun 15, 2026; `claude-sonnet-4-5-20250929` deprecated Sep 30, 2026, retiring Nov 30, 2026; Opus 4.1 retired Aug 5, 2026. API parameters also churn: `temperature`, `top_p` and `top_k` were removed in API version `2026-10-21`. [Vendor docs] — [Claude Platform docs, Model deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations)
  - → Guild: *missing*: a model-upgrade runbook, i.e. a scheduled check that opens an issue when a pinned model is deprecated, mirroring confusable's weekly Unicode-release issue workflow, plus an eval replay before the re-pin.
- **Scaffolding goes stale**: "every component in a harness encodes an assumption about what the model can't do on its own." Sprints were removed on Opus 4.6, and context resets dropped on Opus 4.5. [Vendor] — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps). Spotify removed its LLM judge as models improved. [Secondary] — [InfoQ](https://www.infoq.com/news/2026/03/spotify-honk-rewrite/)
  - → Guild: *missing*: each role and gate in the plugin should record the assumption it encodes ("Planner exists because Builder mis-scopes multi-file changes") so upgrades can test and delete it.
- **Prompts and config as code**: "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." `/doctor` proposes cuts. [Vendor] — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices). Tools should be developed against held-out evals, and "Claude is an expert at analyzing transcripts and refactoring lots of tools." [Vendor] — [Anthropic, Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents). Plugins carry a manifest version, marketplaces distribute versioned releases, and plugin evals exist. [Vendor] — [Claude Code docs, Plugins](https://code.claude.com/docs/en/plugins)
  - → Guild: *supports* the plugin-in-its-own-repo design. *Missing*: per-repo pinning of the Guild plugin version (a marketplace ref or SHA) so a plugin release can't change all repos' behaviour at once, which is the rainbow-deployment lesson. Also an eval suite (replayed issues) run in the plugin's own CI.
- **Portability layers**:
  - claude-code-action supports Anthropic API, Bedrock, Vertex (Google Cloud Agent Platform) and Foundry via OIDC. [Vendor docs] — [Claude Code docs, GitHub Actions](https://code.claude.com/docs/en/github-actions)
  - Agent Skills became an open standard (Dec 18, 2025). [Vendor] — [Anthropic, Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
  - AGENTS.md and MCP are now under the Linux Foundation's AAIF. [Secondary press] — [SD Times](https://sdtimes.com/ai/linux-foundation-forms-agentic-ai-foundation-to-be-new-home-for-mcp-goose-and-agents-md/)
  - gh-aw's Markdown workflow format is engine-agnostic (Copilot, Claude Code, Codex, Gemini, Pi). [Vendor docs] — [gh-aw overview](https://github.github.com/gh-aw/introduction/overview/)
  - Managed Claude Code Review does **not** cover Bedrock- or Vertex-only orgs (it needs a Claude Team or Enterprise org). [Vendor docs] — [Claude Code docs, Code Review](https://code.claude.com/docs/en/code-review)
  - → Guild: *supports* AGENTS.md + skills + `claude -p` + Actions as a portable stack, and *supports* avoiding managed products tied to Anthropic-hosted plans. Remaining lock-in: `.claude/agents/*.md` frontmatter and hooks are Claude Code-specific. That fits Guild's Claude-only scope but would need translating for another engine.
- **Model choice per role**: OpenAI recommends baselining every role on the most capable model, then swapping smaller ones in under evals. [Vendor] — [OpenAI guide PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf). In one small study Haiku 4.5 out-reviewed Sonnet 4.6 at 3.2x lower cost. [Independent, small n] — [arXiv 2606.15689](https://arxiv.org/abs/2606.15689)
  - → Guild: *supports* per-role models in GUILD.md, but they should be set by measurement, not role prestige.

### Inferences
- A pinned Claude model on the Anthropic API has recently lasted ~12-15 months from release to retirement (Sonnet 4: May 2025 → Jun 2026; Sonnet 4.5: Sep 2025 → Nov 2026). Guild should plan at least one forced model migration per year per role, and more often if it follows new releases. The release dates here are my inference from model ID date stamps, not stated on the page.
- The confusable repo's existing "issue, not PR, for upstream releases" pattern (weekly Unicode check) is the right template for model deprecations and Guild-plugin updates.
- Because aliases differ by provider, "portable across Anthropic, Bedrock and Vertex" should mean *same Guild config, different pinned IDs per provider, same evals*, not identical behaviour.

### Gaps
- No public data on how often prompt and skill behaviour regresses across Claude point releases, or on recommended eval-suite sizes for agent pipelines beyond Anthropic's "~20 queries to start."
- I did not read the Claude Code docs section on third-party provider pinning (the page was truncated at 100k characters), so provider-specific pinning advice beyond `ANTHROPIC_DEFAULT_*_MODEL` is unverified.
- I did not verify whether plugin marketplaces support pinning a plugin to a git SHA or tag per project. The docs mention versioned releases but I did not open the publish or marketplace pages.
